# 轻量级 ERP MVP 产品需求文档（MVP-PRD）

-   **文档版本**：v0.1
-   **文档状态**：MVP 范围基线 / 待用户验证
-   **产品形态**：开源、自托管、模块化团队经营管理系统
-   **目标用户**：5--30 人的软件外包公司、技术团队和工作室
-   **技术方向**：React + TypeScript、Go、PostgreSQL、Docker Compose

> 本文只定义第一阶段要交付和验证的内容。插件市场、任意第三方后端代码动态加载、完整低代码和复杂财务系统不属于
> MVP。

------------------------------------------------------------------------

## 1. MVP 目标

### 1.1 核心目标

交付一套能够在用户自己的服务器上运行的轻量经营系统，让小团队能够管理客户、合同、项目和回款，并验证业务模块是否可以按需组合。

### 1.2 核心假设

1.  目标用户愿意使用自托管系统管理客户、合同、项目和回款。
2.  将这些数据关联起来，比使用多份表格更有价值。
3.  用户需要一定程度的字段、状态和流程定制，但早期不需要任意代码级扩展。
4.  采用统一插件契约可以为后续第三方生态打下基础。
5.  Docker Compose 可以满足首批自托管用户的部署需求。

### 1.3 MVP 成功标准

MVP 至少应满足：

-   新用户能按照文档完成部署并创建企业空间。
-   管理员可以邀请成员并分配角色。
-   用户能完成客户、合同、项目和回款的基本业务流程。
-   合同、客户、项目和回款记录之间的关系可追溯。
-   管理员能启用 / 停用官方业务模块（停用不删除业务数据）。
-   管理员能配置有限的自定义字段和状态流转。
-   租户隔离和服务端权限校验通过测试。
-   系统能完成数据库备份与恢复的基本验证。
-   插件模块不需要直接修改其他模块的数据表。

------------------------------------------------------------------------

## 2. 用户与角色

  角色              MVP 权限
  ----------------- --------------------------------------------
  实例管理员        管理部署级设置、插件来源和系统维护能力
  企业管理员        管理企业成员、角色、启用模块和业务配置
  普通成员          访问被授权的业务模块和数据
  模块负责人        在被授予的范围内管理客户、项目、合同或回款
  访客 / 外部客户   MVP 暂不支持

MVP 可以先采用简单
RBAC：角色绑定权限，权限按模块和操作划分；对于"只能查看自己负责的数据"等资源级权限，至少要为项目、客户等关键对象设计可扩展的授权入口。不能只在前端隐藏按钮。

## 3. MVP 功能范围

### 3.1 P0：必须交付

#### A. 平台核心

-   首次启动初始化向导。
-   创建企业空间。
-   登录、退出和会话管理。
-   成员邀请或管理员创建成员。
-   角色与权限配置。
-   基础工作台。
-   菜单根据已启用模块和权限动态展示。
-   插件登记、依赖元数据、启用 / 停用。
-   基础审计日志。
-   健康检查与基础错误提示。
-   Docker Compose 部署与环境变量模板。
-   数据库迁移和基础备份 / 恢复说明。

#### B. CRM 客户模块

-   客户列表、详情、创建、编辑。
-   客户名称、负责人、状态、来源、备注等基础字段。
-   联系人管理。
-   客户跟进记录。
-   搜索、筛选、分页。
-   客户关联合同与项目。
-   自定义字段的基础读取和编辑能力（由平台元数据驱动）。

#### C. 项目模块

-   项目列表、详情、创建、编辑。
-   项目名称、客户、关联合同、负责人、状态、开始 / 计划结束日期。
-   项目任务与负责人。
-   里程碑或简单阶段。
-   任务状态与截止日期。
-   项目进度的基础展示。
-   按负责人、状态、客户筛选。
-   客户与合同关联通过公开模块服务完成。

#### D. 合同模块

-   合同列表、详情、创建、编辑。
-   合同编号、名称、客户、关联项目、金额、签订日期、开始 /
    结束日期、状态、备注。
-   合同状态：草稿、待审批（若启用审批）、生效、已完成、已终止。
-   关联收款计划。
-   合同金额与已收金额的基础汇总。
-   合同列表搜索和筛选。

MVP
不负责电子签章、合同模板自动生成、复杂法务条款分析和电子档案合规管理。

#### E. 回款模块

-   为合同创建一个或多个收款计划。
-   记录计划金额、计划日期和状态。
-   记录实际回款金额、日期、备注。
-   展示计划金额、已收金额、未收金额。
-   根据计划日期和完成情况计算逾期状态。
-   回款记录可追溯到合同、客户。
-   基础逾期提醒可先在工作台显示，不要求首版支持外部消息渠道。

MVP
中的回款管理是经营记录，不是专业会计账务系统。需要明确金额精度、币种策略和部分回款处理规则。

#### F. 自定义字段

-   管理员可以为指定业务实体添加有限的自定义字段。
-   首版字段类型建议支持：单行文本、多行文本、数字、日期、单选、布尔值。
-   字段可以设置名称、标识、是否必填、默认值和选项。
-   表单能够读取元数据并渲染对应控件。
-   服务端必须根据字段定义进行类型和必填校验。
-   字段删除或类型变更需有数据影响提示；首版可限制危险变更。

#### G. 简单工作流

-   为指定实体定义有限状态集合。
-   配置允许的状态转换。
-   按角色控制特定状态转换。
-   支持状态变更记录。
-   支持状态变化后生成站内待办或通知记录。
-   不支持任意脚本、任意 SQL 或复杂并行 BPMN。

首版可先覆盖项目状态与合同状态，避免过早抽象成通用流程设计器。

#### H. 插件基础机制

-   每个官方业务模块拥有唯一插件 ID 和 manifest。
-   manifest 声明版本、平台 API 版本、依赖、权限和导航贡献。
-   启动时校验插件 ID 冲突与版本兼容。
-   注册模块路由、权限和菜单。
-   支持企业级启用 / 停用。
-   插件停用后隐藏入口并拒绝对应 API 操作，但默认保留业务数据。
-   插件数据库迁移有版本记录。
-   安装、启用、停用和迁移行为写入审计日志。

MVP 的官方插件可随宿主一起构建和部署，不要求任意第三方 Go 代码热加载。

### 3.2 P1：有余力再做

-   客户商机看板。
-   文件附件上传。
-   项目时间线。
-   更灵活的列表列配置。
-   CSV 导入 / 导出。
-   邮件通知。
-   简单自动化规则。
-   插件依赖可视化。
-   多语言支持。
-   更完善的资源级权限。

### 3.3 明确不做

-   完整会计、总账、凭证和税务
-   库存、采购、制造、供应链
-   薪酬、考勤、绩效
-   复杂甘特图和完整敏捷管理
-   任意代码工作流
-   在线上传任意 Go 插件并在宿主进程中动态执行
-   插件付费、分账、退款和开发者结算
-   完整第三方插件审核市场
-   微服务化、Kubernetes 交付
-   强制依赖云端账号或联网授权
-   移动端原生 App

## 4. 关键业务流程与验收

### 4.1 客户到回款闭环

1.  企业管理员创建成员并分配角色。
2.  销售成员创建客户和联系人。
3.  销售记录客户跟进。
4.  管理员或有权限成员创建合同，并关联客户。
5.  项目负责人创建项目，可关联客户与合同。
6.  项目负责人创建任务和里程碑，更新项目状态。
7.  合同负责人创建收款计划。
8.  有权限成员记录实际回款。
9.  系统显示已收、未收与逾期信息。
10. 企业负责人在工作台查看有权限范围内的经营概览。

**验收标准：** - 关联关系在页面中可查看并能正确跳转。 -
金额汇总与回款记录一致。 - 部分回款不会错误地将未收金额归零。 -
不同租户用户不能读取或修改彼此的记录。 - 无权限用户无法通过直接调用 API
绕过页面限制。

### 4.2 模块启停

1.  企业管理员打开插件中心。
2.  查看模块名称、版本、依赖和所需权限。
3.  启用模块。
4.  平台校验依赖和兼容性。
5.  菜单与权限按模块状态更新。
6.  停用模块后，普通用户无法进入其页面或调用其业务 API。
7.  重新启用后，原业务数据仍可使用。

**验收标准：** - 启用缺少依赖的模块时给出可理解的错误信息。 -
停用模块不删除数据。 - 通过直接请求 API 不能绕过停用状态。 -
所有状态变化均有审计记录。

### 4.3 自定义字段

1.  管理员选择业务实体。
2.  添加字段并设置类型、必填规则和选项。
3.  系统校验字段标识唯一性。
4.  表单根据元数据显示字段。
5.  用户提交数据。
6.  服务端根据元数据校验并保存。
7.  列表和详情页展示字段值。

**验收标准：** - 不合法类型、缺失必填字段和无效选项会被服务端拒绝。 -
未授权用户不能更改字段定义。 - 字段配置变化有审计记录。 -
字段标识不能与保留字段冲突。

### 4.4 工作流状态转换

1.  管理员配置允许的状态转换。
2.  用户尝试变更实体状态。
3.  服务端校验当前状态、目标状态和用户权限。
4.  校验通过后，在事务中保存状态和历史记录。
5.  生成待办或站内通知。

**验收标准：** - 不允许的状态转换会被拒绝。 -
未授权角色无法执行受限转换。 -
状态记录包含操作人、时间和变更前后状态。 -
重试请求不会重复产生非幂等的副作用。

## 5. MVP 数据模型草案

以下为逻辑实体建议，最终字段以技术设计文档为准。

### 平台核心

-   `tenants`
-   `users`
-   `tenant_members`
-   `roles`
-   `permissions`
-   `role_permissions`
-   `member_roles`
-   `sessions` 或认证相关记录
-   `audit_logs`
-   `plugin_registry`
-   `tenant_plugins`
-   `plugin_migrations`
-   `custom_field_definitions`
-   `workflow_definitions`
-   `workflow_transition_logs`
-   `notifications`

### CRM

-   `customers`
-   `customer_contacts`
-   `customer_activities`

### 项目

-   `projects`
-   `project_tasks`
-   `project_milestones`

### 合同与回款

-   `contracts`
-   `receivable_plans`
-   `payment_records`

### 数据模型原则

-   业务数据具备可靠的租户归属。
-   关键关联关系在服务端校验。
-   金额使用明确精度的 decimal / numeric 类型，不使用浮点数计算货币。
-   自定义字段定义与字段值分离。
-   删除策略需明确：软删除、禁止删除或级联删除应按实体定义。
-   所有关键状态变化都保留历史记录。
-   数据库约束与服务端校验共同保障数据一致性。

## 7. 技术约束与建议

### 7.1 前端

-   React + TypeScript
-   Vite
-   TanStack Query
-   Zustand（仅用于适合的客户端共享状态）
-   Tailwind CSS + shadcn/ui
-   OpenAPI 类型生成可作为后续开发流程的一部分

### 7.2 后端

-   Go
-   Gin HTTP 框架
-   PostgreSQL
-   `pgx` + `sqlc`，或经过统一规范的 ORM
-   `golang-migrate` 数据迁移
-   `log/slog` 日志
-   `go-playground/validator` 请求校验
-   OpenAPI + Scalar 文档
-   标准库测试与必要的集成测试

### 7.3 架构

-   模块化单体。
-   平台核心与业务模块分离。
-   业务模块通过应用服务和公开领域接口交互。
-   领域事件用于通知与异步副作用，不替代需要强一致性的事务。
-   后续可引入 Transactional Outbox 保障事件可靠投递。
-   初期不强制 Redis、Kafka 或微服务。
-   插件接口应可版本化，并有契约测试。

### 7.4 自托管

-   Docker Compose 启动。
-   PostgreSQL 使用持久化卷。
-   环境变量与密钥不写入代码仓库。
-   提供初始化、升级、备份、恢复文档。
-   数据库迁移执行前有备份和失败处理策略。
-   核心功能支持无外网运行。

## 8. MVP 安全要求

-   认证与授权中间件统一执行。
-   所有业务查询强制带入可信租户上下文。
-   对创建、更新、删除和状态转换进行资源级授权。
-   密码使用安全的密码哈希算法存储。
-   Cookie / Token 策略、CSRF 防护和会话失效机制在技术设计中明确。
-   输入校验与数据库参数化查询。
-   上传文件限制类型、大小和存储位置（如 MVP 开启附件）。
-   审计日志不记录明文密码、访问令牌和敏感密钥。
-   插件停用后服务端必须拒绝其业务 API。
-   数据库迁移和插件生命周期操作必须受管理员权限控制。

## 11. MVP 风险

  ---------------------------------------------------------------------------------------
  风险                    影响                     缓解策略
  ----------------------- ------------------------ --------------------------------------
  插件抽象过早            开发速度下降             只抽象实际出现的扩展点，先做官方插件

  自定义字段复杂度失控    查询、索引和迁移困难     限定字段类型，核心字段保持关系型

  权限模型不足            可能发生越权或数据泄露   先实现租户隔离与后端授权测试

  跨模块事务复杂          数据不一致               明确应用服务与事务边界

  自托管升级失败          用户数据风险             迁移版本化、备份与恢复演练

  功能范围过大            MVP 无法交付             P0 必须项优先，P1 延后

  第三方插件安全风险      代码执行和数据泄露       MVP 不执行任意第三方后端代码
  ---------------------------------------------------------------------------------------

## 12. 交付顺序建议

1.  **工程底座**：Go 服务、React
    工程、PostgreSQL、迁移、日志、配置、Docker Compose。
2.  **平台核心**：租户、用户、认证、角色权限、审计。
3.  **插件基础**：manifest、注册器、菜单与权限注册、启停状态。
4.  **CRM**：客户、联系人、跟进记录。
5.  **项目**：项目、任务、里程碑与客户关联。
6.  **合同**：合同与客户、项目关联。
7.  **回款**：计划、实际记录、未收金额和逾期状态。
8.  **配置能力**：自定义字段与有限状态机。
9.  **工作台与体验完善**：经营概览、搜索、空状态、错误处理。
10. **质量与发布**：权限测试、业务闭环 E2E、备份恢复、自托管文档。

建议在每一步都保留可运行版本，不要等所有业务模块完成后才首次部署。

## 13. MVP 评审清单

在进入正式开发前，需要确认：

-   [ ] 是否将"客户 → 合同 → 项目 → 回款"作为首条核心业务闭环？
-   [ ] 项目与合同是否允许多对多关联，还是先采用简单的一对多？
-   [ ] MVP 是否必须支持成员邀请邮件，还是先由管理员创建成员？
-   [ ] 是否首版支持附件上传？
-   [ ] 自定义字段是否只作用于 CRM，还是同时覆盖项目与合同？
-   [ ] 工作流是否先只覆盖项目和合同？
-   [ ] 首版是否支持多个企业租户，还是只允许单企业部署但预留租户模型？
-   [ ] 认证采用 Cookie Session 还是 JWT？
-   [ ] 插件启停按企业生效，还是实例级全局生效？
-   [ ] 开源许可证和官方插件许可证如何选择？

这些决策应在开发前确定；不影响主业务闭环的细节可以在迭代中调整。

# 轻量级 ERP MVP 产品需求文档（MVP-PRD）

- **文档版本**：v0.4
- **更新日期**：2026-10-11
- **文档状态**：平台底座范围基线 / 待实现与用户验证
- **产品形态**：开源、单企业自托管、插件化 ERP 系统；Web 管理端 + App 采集端 + 统一后端 API
- **目标用户**：使用 Excel 记录业务或商品信息的小公司、小商铺
- **技术方向**：React + TypeScript Web 端、Go、PostgreSQL、Docker Compose；App 技术选型待定

> 本阶段先跑通平台底座，用最小示例插件验证完整链路，不承诺正式行业业务系统。扫描、识别、商品、销售、库存、客户、合同、项目和回款等具体功能由后续插件定义；自定义字段、通用工作流和插件市场不属于首版必须交付范围。

## 1. MVP 目标

### 1.1 核心目标

交付可在用户服务器运行的 ERP 平台底座：企业基础信息与成员管理、认证、RBAC、插件注册与启停、审计和部署维护。Web 与 App 通过同一业务 API 操作同一数据，以最小示例插件证明平台可扩展。

每家公司 / 商铺自行部署一套实例，拥有独立数据库、账号和插件配置。项目不提供 SaaS 或厂商云平台；不提供多企业管理、企业切换和跨企业后台。

长期目标是减少 Excel 手工录入并连接现场采集与日常管理；本阶段不验证某个完整行业流程，也不把平台技术验收当成业务价值验证。

### 1.2 核心假设

1. 小公司、小商铺需要减少手工录入并统一管理数据，具体痛点仍需用户验证。
2. Web 管理和 App 现场采集可以共用一套后端业务规则与授权。
3. 平台共用能力与具体业务插件可以保持明确边界。
4. 随宿主构建的官方插件足以验证早期扩展契约，不需要动态执行任意代码。
5. 先验证平台闭环，再按真实用户需求选择正式业务插件，能够控制首版范围。

### 1.3 MVP 成功标准

- 新环境按文档完成部署、初始化企业信息及管理员账号。
- 管理员创建成员、角色，分配平台与插件权限。
- 示例插件完成注册、兼容性 / 依赖校验、迁移和实例级启停。
- Web 与 App 可通过同一 API 创建 / 查询示例记录，数据无需二次录入。
- 未登录、无权限、停用成员与停用插件请求被后端拒绝。
- 关键操作有审计记录；插件停用不删除数据，重新启用后数据仍可使用。
- 数据库备份恢复后，示例数据、授权关系与插件启用状态可验证。
- 示例插件不修改其他模块内部实现或直接操作其业务表。

### 1.4 首版平台闭环

独立部署并初始化企业信息 → 创建成员与角色 → 启用示例插件 → 分配权限 → 两端访问同一业务记录 → 越权与权限撤销验证 → 审计 → 停用 API 拒绝 → 重新启用 / 备份恢复。

## 2. 用户、部署边界与角色

| 角色方向 | 职责 |
| --- | --- |
| 企业管理员 | 初始化企业信息、管理成员与角色、启停已部署插件 |
| 自托管运维人员 | 部署、升级、备份和恢复；不因运维身份自动获得应用内角色 |
| 操作人员 | 执行获授权的插件操作 |
| 查看人员 | 查询获授权的数据，不执行修改 |

角色名称为建议，首版通过角色绑定权限；拥有 App 或 Web 访问入口本身不赋予业务权限。

- **RBAC**：控制成员能执行什么操作；插件声明自己的权限项。
- **部署隔离**：不同企业通过独立实例与数据库隔离，不在同一实例建立多个租户。
- **资源授权**：预留对象级校验入口，不承诺首版完整行级或字段级配置引擎。
- **启用与授权分离**：本实例启用插件不自动给所有成员开放操作权限。
- **双端统一**：同一成员在两端遵循同一业务授权规则。

单企业独立部署已确认，不要求多租户模型或双租户隔离用例。企业内部权限仍必须由后端执行，不能因自托管而省略认证与授权。外部客户 / 访客访问暂不支持。

## 3. MVP 功能范围

### 3.1 P0：必须交付

#### A. 企业、成员与认证

- 首次启动初始化、配置本企业信息并创建管理员账号。
- 管理员创建成员，成员启用 / 停用。
- 两端登录、退出和会话管理，服务端校验企业成员身份。
- 角色与权限配置，统一服务端授权。
- 邮件邀请不作为首版要求。

#### B. 插件基础机制

- 唯一插件 ID、版本、平台 API 兼容版本、依赖、权限、适用端与导航声明。
- 明确业务 API / 服务注册入口与数据库迁移记录。
- 校验 ID 冲突、缺失依赖、不兼容版本和非法依赖关系，给出可理解的错误。
- 支持按实例启用 / 停用；普通成员无权执行插件管理操作。
- 导航按启用状态、适用端和用户权限生成；授权独立于启用。
- 停用后服务端拒绝业务 API，默认保留数据。
- 有已启用依赖方时拒绝直接停用被依赖插件，提示先处理依赖。
- 启停与迁移操作有审计记录。

首版插件与宿主 / 对应客户端一起构建发布。不包含在线安装器、任意第三方代码热加载或运行时移动插件下载。

#### C. Web 管理端平台壳

- 登录、初始化、基础工作台与个人设置。
- 企业成员、角色权限、插件中心和审计查看。
- 按元数据加载随 Web 构建的示例插件入口和界面。
- 工作台先显示有权限的插件入口 / 基础活动，不硬编码经营报表。

#### D. App 采集端平台壳

- 自部署 API 地址配置、登录、个人设置和退出；不提供企业切换。
- 连接企业自行部署的 API，不依赖厂商云服务。
- 仅展示本实例已启用、适用于 App 且有权限访问的插件入口。
- 示例插件提供最小录入与查询能力，与 Web 共用业务 API。
- 提交、加载、权限失效、网络失败等状态有明确反馈，不将失败提交显示为成功。
- 不复制完整 Web 管理后台；不要求所有插件同时支持两端。

App 技术选型和支持的移动系统待确认。本阶段不要求具体扫描、拍照识别、离线同步、推送通知或应用商店发布。

#### E. 统一 API 与数据边界

- 两端共用认证与业务契约，业务规则只在后端维护。
- 每次业务请求验证身份、成员状态、插件启用状态与操作权限。
- 统一输入校验、错误响应和分页约定。
- OpenAPI 与 API 客户端保持同步，客户端类型不参与授权绕过。
- 插件拥有自己的业务数据，通过公开平台契约访问共用能力。

#### F. 最小示例插件

- 使用固定、最小的示例记录结构，不引入通用实体或自定义字段引擎。
- 提供记录创建、列表 / 详情查询、编辑和删除操作及独立权限项。
- 提供 Web 和 App 最小界面；字段和两端具体操作在设计阶段确认。
- 记录存储于本实例数据库，操作人身份由服务端确定，服务端强制操作授权。
- 关键写入操作可审计，重启及重新启用后数据仍可访问。
- 插件迁移与契约可测试，不依赖其他业务插件的内部实现。

示例只用于平台验收，不承诺商品、库存、财务或项目业务。依赖 / 兼容性异常可由测试夹具验证，不要求再交付一个正式业务插件。

#### G. 审计、部署与维护

- 认证相关事件、成员 / 角色 / 权限变更、插件启停 / 迁移及示例关键操作的审计。
- 审计关联本实例操作人、动作、资源、时间和结果，敏感凭证不入日志。
- Docker Compose、环境变量模板、健康检查、数据库迁移。
- 初始化、升级、备份与恢复说明及基本演练。

### 3.2 后续能力，不阻塞平台验收

- 依据用户验证选择首个正式业务插件，另写插件 PRD。
- Skill 管理作为独立能力另写《[Skill 管理插件 PRD](./plugins/PRD-Skill管理插件.md)》：通过插件契约实现，但提供独立一级入口、权限与资产生命周期，不嵌套于插件中心；不依赖业务插件或 AI 执行器，独立排期，暂不加入本 MVP 的 P0。
- 扫码、照片识别、Excel 导入及其他采集 / 集成能力。
- 商品、销售、库存或 CRM / 合同 / 项目 / 回款插件。
- 自定义字段、表单配置、通用工作流与审批。
- 文件附件、通知 / 待办、事件与自动化能力。
- 完善资源级权限、插件 SDK / 脚手架与开发者工具。

不把所有方向默认为下个版本承诺，按实际需求逐项确认。

### 3.3 明确不做

- SaaS、厂商云平台、多租户托管、多企业管理或跨企业后台。
- 完整行业 ERP、会计、制造、供应链或 HRM 系统。
- 通用低代码平台、任意脚本或 SQL 执行。
- 完整第三方插件市场、交易与结算。
- 任意后端或移动端插件代码在线热加载。
- 微服务、Kubernetes 交付或强制云端账号 / 联网授权。
- App 离线业务同步、具体扫描 / 识别引擎及完整后台功能复制。

## 4. 关键流程与验收

### 4.1 初始化、授权与跨端共享

1. 初始化实例并创建企业，由管理员创建成员和角色。
2. 登记示例插件并在本实例启用。
3. 为操作人员授予示例记录创建 / 查询权限，为查看人员仅授予查询权限。
4. 操作人员在 App 创建记录，在 Web 查询同一记录；再验证 Web 创建的数据可由 App 查询。
5. 查看人员直接调用写入 API，后端拒绝；未授权人员无法访问示例记录。
6. 检查关键操作的审计记录。

**验收标准：**

- 两端使用同一后端资源，无二次转录或独立业务数据副本。
- 记录的操作人由服务端会话确定，客户端伪造用户 ID 或角色无法越权。
- 前端显示与权限一致；直接调用 API 无法绕过授权。
- 网络或校验失败不会显示为保存成功。

### 4.2 插件启停与数据保留

1. 管理员查看插件版本、依赖、权限和支持的端。
2. 对有效插件启用；对缺失依赖或不兼容插件拒绝启用。
3. 停用示例插件，使用两端已有会话及缓存入口再次调用 API。
4. 重新启用并查询原记录。

**验收标准：**

- 普通成员不能管理插件，启用不自动授予业务权限。
- 停用后两端入口隐藏，后端拒绝业务操作。
- 有已启用依赖方时拒绝直接停用，不隐式级联删除或停用。
- 停用不删除数据，重新启用后可正常访问，启停均有审计。

### 4.3 企业内部授权与权限撤销

1. 在同一实例准备管理员、操作人员、查看人员与示例记录。
2. 使用未登录请求、查看人员会话或伪造用户 / 角色标识直接调用受限 API，尝试读取 / 修改。
3. 撤销成员写入权限或停用成员，再通过其已有 Web / App 会话尝试访问。

**验收标准：**

- 未登录请求和超出角色权限的读取、修改、删除及审计查询均被拒绝。
- 移除权限后，后续请求立即执行新授权结果，不依赖用户重新登录。
- 停用成员的已有会话不能继续访问业务数据。
- 身份校验、成员状态和 RBAC 均由后端执行，不仅验证菜单隐藏。

### 4.4 迁移、重启与恢复

1. 在空数据库运行核心和示例插件迁移，创建记录与授权关系。
2. 重启系统，确认状态与数据保持。
3. 备份数据库，恢复至新环境，验证记录、角色权限和实例插件状态。

**验收标准：**

- 迁移结果与版本可追溯，不重复破坏已有数据。
- 重启和恢复后两端可按原授权访问记录，停用状态不能丢失。
- 迁移失败或不满足兼容要求时，不把不可用插件暴露为可操作入口。
- 恢复说明包含部署配置与密钥的处理方式，不将敏感值提交仓库。

## 5. MVP 数据模型草案

以下为逻辑实体方向，最终字段与存储方式在技术设计中定义。

### 平台核心

- `company_settings`（单实例企业信息）、`users`（本企业成员）
- `roles`、`permissions`、`role_permissions`、`user_roles`
- `sessions` 或等效的认证记录
- `audit_logs`
- `plugin_registry`、`instance_plugins`、`plugin_migrations`

### 最小示例插件

- 示例记录表（暂称 `example_records`）：固定最小字段和必要操作追踪。
- 示例插件的迁移与权限元数据。

### 数据原则

- 企业成员、角色、插件启用状态和业务记录均属于当前独立实例；不要求租户 ID 或租户成员关系。
- 权限声明与角色赋权分离；适用端元数据不改变权限。
- 关键关联由数据库约束和服务端共同校验。
- 插件不直接写入其他业务模块的数据表。
- 示例删除策略在技术设计中确定，审计历史不得随业务记录删除。
- 不在首版预建商品、库存、客户、合同、项目、回款、通用工作流或自定义字段 schema。

## 6. 页面与导航

### Web

- 登录、首次初始化、基础工作台、个人设置。
- 企业成员、角色与权限、插件中心、审计和基础设置。
- 示例插件列表、详情和最小编辑界面。

### App

- 自部署 API 地址配置、登录与个人设置，不提供企业切换。
- 插件入口列表。
- 示例记录最小录入与查询界面。

### 交互要求

- 按实例启用状态、适用端与权限生成入口。
- 列表具备分页、加载、空态与错误态。
- 停用、删除及危险配置需要明确确认。
- 表单指出具体校验错误；失败提交不显示成功。
- 会话失效、权限撤销或插件停用后提供可理解的反馈。
- App 网络失败保留当前输入供用户处理，不在首版承诺后台自动重试 / 离线同步。
- 关键操作不依赖前端校验或按钮隐藏。

## 7. 技术约束与建议

### 7.1 Web 与 App

**Web 技术方向：**

-   React + TypeScript
-   Vite
-   TanStack Query
-   Zustand（仅用于适合的客户端共享状态）
-   Tailwind CSS + shadcn/ui

**App 与双端约束：**

-   App 原生或跨平台技术、支持的移动系统和打包交付方式待确认。
-   两端共用后端业务 API，适用客户端从 OpenAPI 生成或校验类型。
-   API 变化同步维护 OpenAPI 与 API 客户端包。
-   App 插件 UI 首版静态构建注册，不要求运行时下载执行任意代码。
-   摄像头、扫描和识别能力留到正式插件阶段，不作为平台壳验收。

### 7.2 后端

-   Go
-   Gin HTTP 框架
-   PostgreSQL
-   `pgx` + `sqlc`，或经过统一规范的 ORM
-   `golang-migrate` 数据迁移
-   `log/slog` 日志
-   `go-playground/validator` 请求校验
-   OpenAPI + Scalar 文档
-   标准库测试与必要的集成测试

### 7.3 架构

-   模块化单体。
-   平台核心与业务模块分离。
-   平台契约由核心提供，插件不依赖其他模块内部实现或直接写入其数据表。
-   App 不维护独立业务后端，管理与采集请求经过同一授权边界。
-   业务模块通过应用服务和公开领域接口交互。
-   领域事件用于通知与异步副作用，不替代需要强一致性的事务。
-   后续可引入 Transactional Outbox 保障事件可靠投递。
-   初期不强制 Redis、Kafka 或微服务。
-   插件接口应可版本化，并有契约测试。

### 7.4 自托管

-   Docker Compose 启动。
-   PostgreSQL 使用持久化卷。
-   环境变量与密钥不写入代码仓库。
-   提供初始化、升级、备份、恢复文档。
-   数据库迁移执行前有备份和失败处理策略。
-   核心功能支持无外网运行。

## 8. MVP 安全要求

-   认证与授权中间件统一执行。
-   所有业务请求验证本实例账号身份与成员状态，不信任客户端自报的用户或角色。
-   对业务读写强制执行成员状态、插件状态和操作权限校验，并保留资源级授权入口。
-   密码使用安全的密码哈希算法存储。
-   Cookie / Token 策略、CSRF 防护和会话失效机制在技术设计中明确。
-   输入校验与数据库参数化查询。
-   App 凭证存储、HTTPS 访问与会话失效策略在技术设计中明确；首版不包含附件上传。
-   审计日志不记录明文密码、访问令牌和敏感密钥。
-   权限撤销或插件停用后服务端必须拒绝后续未授权请求，不能依赖客户端缓存刷新。
-   数据库迁移和插件生命周期操作必须受管理员权限控制。

## 9. MVP 测试策略

### 单元与契约测试

- RBAC 判断、会话身份与成员状态校验。
- 插件 ID、依赖、版本兼容性、适用端和启停规则。
- 示例插件字段校验、操作授权和平台契约。
- OpenAPI 与客户端契约一致性。

### 集成测试

- PostgreSQL 核心 / 插件迁移与数据访问。
- 未登录访问、未授权操作、成员停用与权限撤销。
- 插件停用后 API 拒绝、重新启用后数据保留。
- 审计追踪和备份恢复基本流程。

### 双端端到端测试

- 企业初始化、成员创建、角色赋权与插件启用。
- App 创建、Web 查询；Web 创建、App 查询。
- 查看角色无法写入，缓存入口和已有会话无法绕过授权。
- 插件停用、重新启用及错误 / 网络失败反馈。

### 发布前检查

- 全部 P0 验收用例通过，Web 与选定 App 交付方式均可运行。
- 新环境部署、迁移、重启、备份恢复按文档验证。
- 不使用不安全默认密钥，错误响应不泄露堆栈或凭证。
- 示例插件不引入未声明的正式业务范围。

## 11. MVP 风险

| 风险 | 影响 | 缓解策略 |
| --- | --- | --- |
| 泛化 ERP 范围膨胀 | 平台底座无法交付 | 用最小示例验收，正式业务另写插件 PRD |
| 平台抽象过早 | 通用引擎复杂且缺少需求验证 | 字段、工作流和事件按实际需求建设 |
| App 与 Web 双端成本 | 开发范围扩大 | App 只做平台壳和示例入口，不复制后台 |
| 客户端授权不一致 | 越权或停用绕过 | 后端统一执行认证、成员状态、插件状态和权限校验 |
| 第三方代码安全 | 任意代码执行 | 首版仅部署随宿主构建的受信任插件 |
| 升级与恢复失败 | 数据或授权状态丢失 | 版本化迁移和包含授权 / 插件状态的恢复演练 |
| 技术验收替代价值验证 | 平台完成但用户不使用 | 后续以真实插件衡量减少手工录入的效果 |

------------------------------------------------------------------------

## 12. 交付顺序建议

1. 确认 App 交付方式、认证与权限边界、示例插件验收数据。
2. 工程底座：Go API、Web、App 基础工程、PostgreSQL、迁移和 Compose。
3. 平台核心：单实例企业信息、成员、认证、RBAC 与审计。
4. 插件基础：manifest、注册、权限 / 导航贡献、依赖兼容校验与实例级启停。
5. 示例插件：固定字段、业务 API、迁移与操作授权。
6. 双端验证：Web / App 入口、共享记录、越权 / 停用拒绝与错误反馈。
7. 发布验证：权限测试、跨端 E2E、升级和备份恢复演练。
8. 平台验收后，再讨论首个正式业务插件，不提前扩大 P0。

每一步保留可运行版本，不等全部平台功能完成后才首次部署。

## 13. 已确认决策与待确认事项

### 已确认

- [x] 首版聚焦 ERP 平台底座，不细化正式业务功能。
- [x] 扫码 / 识别等能力通过插件扩展，不放入平台核心。
- [x] Web 与 App 共用后端业务 API，由后端统一执行 RBAC。
- [x] 开源自托管：一家公司 / 商铺独立部署一套实例，不提供 SaaS 或厂商云平台。
- [x] 不做同一实例多企业管理；不同企业通过独立实例、数据库、账号和插件配置隔离。
- [x] 插件随宿主 / 客户端构建，按实例启停，默认保留数据。
- [x] 插件可仅支持 Web、仅支持 App 或支持两端。
- [x] 用最小示例插件验证授权、跨端数据、审计、启停和恢复。
- [x] 自定义字段、通用工作流和完整插件市场暂不作为首版必须项。

### 待确认

- [ ] 企业管理员、运维人员和业务成员的具体职责与默认权限。
- [ ] Web / App 认证方案、凭证存储、会话失效及 API 地址配置。
- [ ] App 技术路线、支持的移动系统和可验收交付方式。
- [ ] 示例插件固定字段、删除策略与两端最小操作集合。
- [ ] 权限标识、默认角色、依赖版本规则与客户端注册契约。
- [ ] 开源许可证、升级与备份恢复操作规范。

正式业务插件阶段另行确认采集对象、识别方式、业务规则、自定义能力和效果指标，不以未确认内容阻塞平台讨论。

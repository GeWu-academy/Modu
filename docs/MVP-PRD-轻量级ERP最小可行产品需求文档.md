# 轻量级 ERP MVP 产品需求文档（MVP-PRD）

- **文档版本**：v0.5
- **更新日期**：2026-10-11
- **文档状态**：平台底座范围基线 / 待实现与用户验证
- **产品形态**：开源、单企业自托管、插件化 ERP 系统；Web 管理端 + App 采集端 + 统一后端 API
- **目标用户**：使用 Excel 记录业务或商品信息的小公司、小商铺
- **技术方向**：React + TypeScript Web 端、Go、PostgreSQL、Docker Compose；App 技术选型待定

> 本阶段先跑通平台底座，用最小示例插件验证完整链路，不承诺正式行业业务系统。扫描、识别、商品、销售、库存、客户、合同、项目和回款等具体功能由后续插件定义；自定义字段、通用工作流和插件市场不属于首版必须交付范围。

## 1. MVP 目标

### 1.1 核心目标

交付可在用户服务器运行的 ERP 平台底座：企业基础信息、用户账号与个人空间、认证、RBAC、个人资产归属校验、插件注册与两级启停 / 配置、分域审计和部署维护。Web 与 App 通过同一业务 API 操作同一用户的个人数据，以最小示例插件证明平台可扩展。

每家公司 / 商铺自行部署一套实例，拥有独立数据库、账号和插件配置。项目不提供 SaaS 或厂商云平台；不提供多企业管理、企业切换和跨企业后台。

长期目标是减少 Excel 手工录入并连接现场采集与日常管理；本阶段不验证某个完整行业流程，也不把平台技术验收当成业务价值验证。

### 1.2 核心假设

1. 小公司、小商铺需要减少手工录入并统一管理数据，具体痛点仍需用户验证。
2. Web 管理和 App 现场采集可以共用一套后端业务规则与授权。
3. 平台共用能力与具体业务插件可以保持明确边界。
4. 随宿主构建的官方插件足以验证早期扩展契约，不需要动态执行任意代码。
5. 先验证平台闭环，再按真实用户需求选择正式业务插件，能够控制首版范围。

### 1.3 MVP 成功标准

- 新环境按文档完成部署，初始化企业基础信息、测试账号、个人空间与角色绑定；账号维护机制另行确认。
- 平台插件管理员仅管理平台插件；普通用户可使用已开放插件并独立保存个人配置。
- 示例插件完成注册、兼容性 / 依赖校验、迁移、平台开放 / 停用与个人启用 / 停用。
- 同一用户的 Web 与 App 可通过同一 API 创建 / 查询个人示例记录，数据无需二次录入。
- 未登录、无权限、停用账号、两级停用后的业务请求，以及跨用户 / 管理员访问个人配置、资产和业务审计的请求，均被后端拒绝。
- 关键操作有分域审计记录；两级插件停用保留个人配置与资产，重新开放 / 启用后按原归属与个人启用状态访问。
- 数据库备份恢复后，示例数据、个人配置、资产归属、授权关系与两级插件状态可验证。
- 示例插件不修改其他模块内部实现或直接操作其业务表。

### 1.4 首版平台闭环

独立部署并初始化企业信息 → 建立账号、个人空间与角色绑定 → 平台开放示例插件 → 用户独立启用与配置 → 本人两端访问个人业务记录 → RBAC / 归属与管理员边界验证 → 分域审计 → 两级停用 API 拒绝 → 恢复个人选择、配置与资产 / 备份恢复。

## 2. 用户、个人空间与角色

| 角色方向 | 职责 |
| --- | --- |
| 平台插件管理员 | 仅管理平台插件的登记、配置、开放、停用与受控更新；不管理账号、角色、个人配置或个人资产 |
| 普通用户 | 启用已开放插件并保存个人配置，按权限操作本人的资产 |
| 自托管运维人员 | 负责部署、迁移、备份和恢复；与应用层平台插件管理角色分开 |

角色名称为建议，首版通过角色绑定权限；拥有 App 或 Web 访问入口本身不赋予业务权限。账号开通、角色绑定及其维护机制待确认。

- **RBAC**：控制用户能执行什么操作；插件声明自己的权限项。
- **资产归属**：控制可以访问谁的数据；个人配置、业务记录和后续文件归本人所有，服务端必须校验所有者。
- **共享能力，不共享资产**：管理员开放的插件对所有用户可用，个人启用状态与配置独立，资产默认不共享。
- **管理与业务分离**：平台插件管理员不能读取、修改或删除他人的配置、资产或业务审计，不设置默认管理员绕过。兼有普通用户权限时也只能访问自己的个人空间。
- **启用与授权分离**：业务访问同时满足平台已开放、本人已启用、操作权限与本人资产归属；开放或启用不自动赋予全部操作权限，也不授予跨用户权限。
- **双端统一**：同一用户在两端遵循同一授权与个人数据边界。

每家公司 / 商铺独立部署一套实例；首版以个人工作空间隔离该实例内的多个用户，不提供多企业管理、团队资产共享或外部访客访问。测试至少覆盖两个普通用户和一个平台插件管理员。

“管理员不可访问个人资产”是应用 / API 层面的约束，不承诺阻止拥有服务器、数据库或备份访问权的运维人员读取底层数据。

## 3. MVP 功能范围

### 3.1 P0：必须交付

#### A. 个人空间与认证

- 首次启动初始化；用户账号关联独立个人工作空间。
- 两端登录、退出和会话管理，服务端校验用户身份与账号状态。
- 角色绑定权限，统一执行服务端操作授权与个人资产归属校验。
- 平台插件管理员不默认承担账号、角色维护职责；具体账号开通和角色绑定机制待确认。
- 邮件邀请不作为首版要求。

#### B. 插件基础机制

- 唯一插件 ID、版本、平台 API 兼容版本、依赖、权限、适用端与导航声明。
- 明确业务 API / 服务注册入口与数据库迁移记录。
- 校验 ID 冲突、缺失依赖、不兼容版本和非法依赖关系，给出可理解的错误。
- 平台插件管理员维护平台级插件配置与开放 / 停用；普通用户不能修改平台插件设置。
- 已开放插件对所有用户可用；用户独立启用 / 停用并维护本人配置，不能修改其他人的配置。
- 平台配置、个人配置与业务资产分开；个人配置不向管理员或其他用户开放，平台更新不覆盖已有个人配置，具体初始化规则待确认。
- 业务导航按平台开放、个人启用、适用端与权限生成；插件目录与本人启停 / 配置接口独立授权，不要求已启用才能首次启用。
- 个人停用仅拒绝本人的该插件业务 API；平台停用拒绝所有用户的该插件业务 API，均保留个人配置与资产。
- 重新开放不改变原个人选择，重新启用不改变资产归属。
- 依赖检查覆盖平台开放与个人启用两个范围；存在有效依赖方时拒绝直接停用被依赖插件，提示先处理依赖。
- 平台配置 / 开放 / 停用、个人配置 / 启停与迁移均有分域审计。

首版插件与宿主 / 对应客户端一起构建发布。不包含在线安装器、任意第三方代码热加载、个人上传插件代码或运行时移动插件下载。

#### C. Web 管理端平台壳

- 登录、初始化、基础工作台与个人设置。
- 个人插件中心、个人配置与本人业务审计；平台插件管理员使用独立的平台插件管理与插件管理审计入口。
- 按元数据加载随 Web 构建的示例插件入口和界面。
- 工作台先显示有权限的插件入口 / 基础活动，不硬编码经营报表。

#### D. App 采集端平台壳

- 自部署 API 地址配置、登录、个人工作空间、个人设置和退出；不提供企业切换。
- 连接企业自行部署的 API，不依赖厂商云服务。
- 个人插件中心：查看已开放插件，维护本人启用状态与配置，不包含平台插件管理后台。
- 业务入口仅展示平台已开放、本人已启用、适用于 App 且有权限访问的插件；个人插件中心提供独立启用入口。
- 示例插件提供最小录入与查询能力，与 Web 共用业务 API。
- 提交、加载、权限失效、网络失败等状态有明确反馈，不将失败提交显示为成功。
- 不复制完整 Web 管理后台；不要求所有插件同时支持两端。

App 技术选型和支持的移动系统待确认。本阶段不要求具体扫描、拍照识别、离线同步、推送通知或应用商店发布。

#### E. 统一 API 与数据边界

- 两端共用认证与业务契约，业务规则只在后端维护。
- 每次业务请求验证身份、账号状态、平台开放状态、个人启用状态、RBAC 操作权限与本人资产归属；创建时由后端指定所有者，不接受客户端改变归属。
- 统一输入校验、错误响应和分页约定。
- OpenAPI 与 API 客户端保持同步，客户端类型不参与授权绕过。
- 插件维护自身业务数据结构与写入规则，通过公开平台契约访问共用能力；业务资产归当前用户所有，不归平台插件管理员。

#### F. 最小示例插件

- 使用固定、最小的示例记录结构，不引入通用实体或自定义字段引擎。
- 提供记录创建、列表 / 详情查询、编辑和删除操作及独立权限项。
- 提供 Web 和 App 最小界面；字段和两端具体操作在设计阶段确认。
- 记录存储于本实例数据库，资产归本人所有；操作人和所有者分别记录并由服务端确定，所有读写强制执行操作授权与所有者校验。
- 关键写入操作可审计，重启及重新启用后数据仍可访问。
- 插件迁移与契约可测试，不依赖其他业务插件的内部实现。

示例只用于平台验收，不承诺商品、库存、财务或项目业务。依赖 / 兼容性异常可由测试夹具验证，不要求再交付一个正式业务插件。

#### G. 审计、部署与维护

- 认证相关事件、账号状态 / 角色 / 权限变更（维护机制待确认）、平台与个人插件配置 / 启停、迁移及示例关键操作的分域审计。
- 审计关联本实例操作人、资产所有者（适用时）、动作、资源、时间和结果，不记录业务正文、个人配置敏感值或凭证。平台插件管理员仅查看平台插件管理审计，普通用户仅查看本人业务审计；账号 / 角色等其他系统审计的访问机制待确认，不默认开放给平台插件管理员。
- Docker Compose、环境变量模板、健康检查、数据库迁移。
- 初始化、升级、备份与恢复说明及基本演练。

### 3.2 后续能力，不阻塞平台验收

- 依据用户验证选择首个正式业务插件，另写插件 PRD。
- Skill 管理作为独立能力另写《[Skill 管理插件 PRD](./plugins/PRD-Skill管理插件.md)》：通过插件契约实现，但提供独立一级入口、权限与资产生命周期，不嵌套于插件中心；不依赖业务插件或 AI 执行器，独立排期，暂不加入本 MVP 的 P0。
- 扫码、照片识别、Excel 导入及其他采集 / 集成能力。
- 商品、销售、库存或 CRM / 合同 / 项目 / 回款插件。
- 自定义字段、表单配置、通用工作流与审批。
- 文件附件、通知 / 待办、事件与自动化能力。
- 完善复杂行级 / 字段级权限配置、插件 SDK / 脚手架与开发者工具；个人所有者校验属于首版必须项。

不把所有方向默认为下个版本承诺，按实际需求逐项确认。

### 3.3 明确不做

- SaaS、厂商云平台、多租户托管、多企业管理或跨企业后台。
- 完整行业 ERP、会计、制造、供应链或 HRM 系统。
- 通用低代码平台、任意脚本或 SQL 执行。
- 企业共享空间、团队共享资产、跨用户资产授权与资产转移。
- 个人任意上传或安装插件代码。
- 完整第三方插件市场、交易与结算。
- 任意后端或移动端插件代码在线热加载。
- 微服务、Kubernetes 交付或强制云端账号 / 联网授权。
- App 离线业务同步、具体扫描 / 识别引擎及完整后台功能复制。

## 4. 关键流程与验收

### 4.1 初始化、个人配置与跨端访问

1. 初始化实例，准备普通用户 A、B 的账号、个人空间与测试角色权限。
2. 平台插件管理员登记、配置并开放示例插件。
3. A、B 各自启用插件并保存不同个人配置；角色可分别具有创建 / 查询或仅查询权限。
4. A 在 App 创建记录，在 Web 查询同一记录；再验证 A 在 Web 创建的数据可由自己的 App 查询。
5. 缺少写入权限的用户直接调用写入 API，后端拒绝；B 即使具有相同查询权限也不能查询 A 的记录。
6. 检查平台插件管理审计与各用户的个人业务审计。

**验收标准：**

- 同一用户两端使用同一份个人数据，无二次转录或独立业务数据副本。
- A、B 个人配置互不影响；本人不能修改平台配置或他人配置。
- 创建记录时所有者由后端认证上下文决定，客户端伪造所有者 ID 无法代他人创建或改变归属。
- 前端显示与权限一致；直接调用 API 无法绕过 RBAC 或所有者校验。
- 网络或校验失败不会显示为保存成功。

### 4.2 两级插件启停与数据保留

1. 管理员查看插件版本、依赖、权限和支持的端，对有效插件开放，对缺失依赖或不兼容插件拒绝开放。
2. A、B 各自启用并保存个人配置和记录；A 个人停用后，通过已有会话及缓存入口再次调用业务 API。
3. 平台管理员停用插件，A、B 均通过已有会话或直接调用尝试使用该插件。
4. 平台重新开放：B 恢复可用，A 仍保持个人停用；A 本人重新启用后查询原记录和配置。

**验收标准：**

- 普通用户不能管理平台插件，但可以管理本人启用状态与配置；平台插件管理员不能管理他人的个人配置。
- 个人停用仅隐藏本人入口并拒绝本人业务请求，不影响 B；平台停用隐藏所有人的入口并拒绝所有业务请求。
- 平台开放和个人启用不自动授予全部操作权限，所有者校验始终有效。
- 两级范围内有有效依赖方时拒绝直接停用，不隐式级联删除或停用。
- 停用保留数据和配置，恢复时保留个人选择与资产归属，操作有分域审计。

### 4.3 个人资产隔离、管理员边界与权限撤销

1. 在测试环境准备普通用户 A、B、平台插件管理员及 A、B 各自配置和记录；让 A、B 拥有相同业务权限。
2. B 通过伪造所有者标识、A 的记录 / 配置 ID、列表筛选及直接 API 请求尝试访问 A 的数据。
3. 平台插件管理员尝试读取、修改或删除 A 的个人配置 / 资产，以及查询 A 的业务审计。
4. 撤销 A 的写入权限或停用账号，再通过其已有 Web / App 会话尝试访问。

**验收标准：**

- B 与管理员均不能读取、修改或删除 A 的个人配置和业务资产；列表、详情、关联查询与业务审计均不泄露他人数据。
- 管理员仍能管理平台插件及查看平台插件管理审计，但该审计不包含个人业务正文、配置敏感值或凭证。
- 相同角色、相同插件操作权限、不同客户端与管理员身份均不绕过所有者校验。
- 移除权限后，后续请求立即执行新授权结果，不依赖用户重新登录。
- 停用账号的已有会话不能继续访问业务数据。
- RBAC、个人资产隔离与两级插件状态均由后端执行，不仅验证菜单隐藏。

### 4.4 迁移、重启与恢复

1. 在空数据库运行核心和示例插件迁移，创建记录与授权关系。
2. 重启系统，确认状态与数据保持。
3. 备份数据库，恢复至新环境，验证记录、个人配置、资产归属、角色权限以及平台开放 / 个人启用状态。

**验收标准：**

- 迁移结果与版本可追溯，不重复破坏已有数据。
- 重启和恢复后本人两端可按原授权访问记录，个人配置、资产归属与两级插件状态不能丢失，不扩大跨用户或管理员权限。
- 迁移失败或不满足兼容要求时，不把不可用插件暴露为可操作入口。
- 恢复说明包含部署配置与密钥的处理方式，不将敏感值提交仓库。

## 5. MVP 数据模型草案

以下为逻辑实体方向，最终字段与存储方式在技术设计中定义。

### 平台核心

- `company_settings`（单实例企业基础信息）、`users`（实例内用户账号，关联独立个人空间）
- `roles`、`permissions`、`role_permissions`、`user_roles`
- `sessions` 或等效的认证记录
- `audit_logs`（区分平台插件管理、个人业务及其他系统审计，个人业务审计关联所有者）
- `plugin_registry`、`platform_plugins`（实例内平台配置与开放状态）、`user_plugins`（用户 / 插件唯一关联、个人配置与启用状态）、`plugin_migrations`

### 最小示例插件

- 示例记录表（暂称 `example_records`）：固定最小字段、`owner_user_id` 或等效可靠归属，以及必要操作追踪；所有者与最后操作人不是同一概念。
- 示例插件的迁移与权限元数据。

### 数据原则

- 企业信息、用户账号、角色、插件配置与业务记录均存于当前独立实例；不要求租户 ID 或租户成员关系。实例隔离不能代替实例内个人配置与业务资产隔离。
- 权限声明、角色赋权与资产归属分离；适用端元数据不改变权限。平台插件管理员无个人数据访问特权。
- 个人配置与业务数据由服务端绑定所有者，客户端不能指定或修改他人归属；首版不提供资产转移。
- 平台开放状态与个人启用状态独立持久化；两级停用保留个人配置与资产，平台重新开放不改变个人选择。
- 关键关联由数据库约束和服务端共同校验。
- 插件不直接写入其他业务模块的数据表。
- 示例删除策略在技术设计中确定，审计历史不得随业务记录删除。
- 不在首版预建商品、库存、客户、合同、项目、回款、通用工作流或自定义字段 schema。

## 6. 页面与导航

### Web

- 登录、首次初始化、基础工作台、个人设置。
- 个人插件中心、配置、业务审计和个人设置；平台插件管理及其审计入口仅对平台插件管理员展示。
- 示例插件列表、详情和最小编辑界面。

### App

- 自部署 API 地址配置、登录与个人设置，不提供企业切换。
- 个人插件中心（本人启停 / 配置）与插件业务入口列表。
- 示例记录最小录入与查询界面。

### 交互要求

- 业务入口按平台开放状态、个人启用状态、适用端与权限生成；个人插件中心与本人启停 / 配置接口独立授权，不要求已启用才能首次启用。
- 列表具备分页、加载、空态与错误态。
- 停用、删除及危险配置需要明确确认。
- 表单指出具体校验错误；失败提交不显示成功。
- 会话失效、权限撤销或插件停用后提供可理解的反馈。
- App 网络失败保留当前输入供用户处理，不在首版承诺后台自动重试 / 离线同步。
- 关键操作不依赖前端校验或按钮隐藏。

## 7. 技术约束与建议

### 7.1 Web 与 App

**Web 技术方向：**

-   React + TypeScript
-   Vite
-   TanStack Query
-   Zustand（仅用于适合的客户端共享状态）
-   Tailwind CSS + shadcn/ui

**App 与双端约束：**

-   App 原生或跨平台技术、支持的移动系统和打包交付方式待确认。
-   两端共用后端业务 API，适用客户端从 OpenAPI 生成或校验类型。
-   API 变化同步维护 OpenAPI 与 API 客户端包。
-   App 插件 UI 首版静态构建注册，不要求运行时下载执行任意代码。
-   摄像头、扫描和识别能力留到正式插件阶段，不作为平台壳验收。

### 7.2 后端

-   Go
-   Gin HTTP 框架
-   PostgreSQL
-   `pgx` + `sqlc`，或经过统一规范的 ORM
-   `golang-migrate` 数据迁移
-   `log/slog` 日志
-   `go-playground/validator` 请求校验
-   OpenAPI + Scalar 文档
-   标准库测试与必要的集成测试

### 7.3 架构

-   模块化单体。
-   平台核心与业务模块分离。
-   平台契约由核心提供，插件不依赖其他模块内部实现或直接写入其数据表。
-   App 不维护独立业务后端，管理与采集请求经过同一授权边界。
-   业务模块通过应用服务和公开领域接口交互。
-   领域事件用于通知与异步副作用，不替代需要强一致性的事务。
-   后续可引入 Transactional Outbox 保障事件可靠投递。
-   初期不强制 Redis、Kafka 或微服务。
-   插件接口应可版本化，并有契约测试。

### 7.4 自托管

-   Docker Compose 启动。
-   PostgreSQL 使用持久化卷。
-   环境变量与密钥不写入代码仓库。
-   提供初始化、升级、备份、恢复文档。
-   数据库迁移执行前有备份和失败处理策略。
-   核心功能支持无外网运行。

## 8. MVP 安全要求

-   认证与授权中间件统一执行。
-   所有业务请求验证本实例账号身份与账号状态，不信任客户端自报的用户、角色或所有者。
-   对业务读写强制执行账号状态、平台开放状态、个人启用状态、RBAC 操作权限和本人资产归属校验；所有者校验不是仅预留的后续能力，平台插件管理员不能绕过。
-   个人配置和个人业务审计同样校验所有者；列表、详情、关联查询与后台任务不能泄露其他用户数据。
-   插件目录及本人启停 / 配置接口独立授权，平台配置接口仅对平台插件管理权限开放。
-   密码使用安全的密码哈希算法存储。
-   Cookie / Token 策略、CSRF 防护和会话失效机制在技术设计中明确。
-   输入校验与数据库参数化查询。
-   App 凭证存储、HTTPS 访问与会话失效策略在技术设计中明确；首版不包含附件上传。
-   审计日志不记录明文密码、访问令牌和敏感密钥。
-   权限撤销或插件停用后服务端必须拒绝后续未授权请求，不能依赖客户端缓存刷新。
-   数据库迁移与平台插件生命周期操作受受控发布 / 平台插件管理权限约束；个人启停与配置仅由本人执行。

## 9. MVP 测试策略

### 单元与契约测试

- RBAC 判断、会话身份、账号状态、所有者校验与平台插件管理员无默认绕过。
- 插件 ID、依赖、版本兼容性、适用端、两级启停规则与个人配置隔离。
- 示例插件字段校验、操作授权和平台契约。
- OpenAPI 与客户端契约一致性。

### 集成测试

- PostgreSQL 核心 / 插件迁移与数据访问。
- 未登录访问、未授权操作、账号停用与权限撤销；相同业务权限的 A / B 个人配置和资产隔离、管理员访问拒绝。
- 个人停用仅影响本人，平台停用影响所有用户；恢复后个人选择、配置与资产归属保留。
- 审计追踪和备份恢复基本流程。

### 双端端到端测试

- 个人空间初始化、角色绑定、平台开放与各用户独立启用 / 配置。
- 同一用户 App 创建、Web 查询；Web 创建、App 查询，其他用户与管理员均不可访问。
- 缺少写入权限时不可写入；相同业务权限也不可访问他人资产，缓存入口和已有会话无法绕过授权。
- 插件停用、重新启用及错误 / 网络失败反馈。

### 发布前检查

- 全部 P0 验收用例通过，Web 与选定 App 交付方式均可运行。
- 新环境部署、迁移、重启、备份恢复按文档验证。
- 不使用不安全默认密钥，错误响应不泄露堆栈或凭证。
- 示例插件不引入未声明的正式业务范围。

## 11. MVP 风险

| 风险 | 影响 | 缓解策略 |
| --- | --- | --- |
| 泛化 ERP 范围膨胀 | 平台底座无法交付 | 用最小示例验收，正式业务另写插件 PRD |
| 平台抽象过早 | 通用引擎复杂且缺少需求验证 | 字段、工作流和事件按实际需求建设 |
| App 与 Web 双端成本 | 开发范围扩大 | App 只做平台壳和示例入口，不复制后台 |
| 客户端授权不一致 | 越权或停用绕过 | 后端统一执行认证、账号状态、两级插件状态、RBAC 与个人资产归属校验，不设管理员绕过 |
| 第三方代码安全 | 任意代码执行 | 首版仅部署随宿主构建的受信任插件 |
| 升级与恢复失败 | 数据或授权状态丢失 | 版本化迁移和包含授权 / 插件状态的恢复演练 |
| 技术验收替代价值验证 | 平台完成但用户不使用 | 后续以真实插件衡量减少手工录入的效果 |

------------------------------------------------------------------------

## 12. 交付顺序建议

1. 确认 App 交付方式、认证方案、账号开通 / 角色绑定机制、配置初始化规则与示例插件验收数据。
2. 工程底座：Go API、Web、App 基础工程、PostgreSQL、迁移和 Compose。
3. 平台核心：单实例企业基础信息、用户账号 / 个人空间、认证、RBAC、所有者校验与分域审计。
4. 插件基础：manifest、注册、权限 / 导航贡献、依赖兼容校验、平台开放 / 停用与个人启停 / 配置。
5. 示例插件：固定字段、业务 API、迁移、操作授权与个人资产归属。
6. 双端验证：Web / App 入口、本人跨端记录、跨用户 / 管理员访问拒绝、两级停用与错误反馈。
7. 发布验证：权限测试、跨端 E2E、升级和备份恢复演练。
8. 平台验收后，再讨论首个正式业务插件，不提前扩大 P0。

每一步保留可运行版本，不等全部平台功能完成后才首次部署。

## 13. 已确认决策与待确认事项

### 已确认

- [x] 首版聚焦 ERP 平台底座，不细化正式业务功能。
- [x] 扫码 / 识别等能力通过插件扩展，不放入平台核心。
- [x] Web 与 App 共用后端业务 API，由后端统一执行 RBAC 与个人资产归属校验。
- [x] 开源自托管：一家公司 / 商铺独立部署一套实例，不提供 SaaS 或厂商云平台。
- [x] 不做同一实例多企业管理；不同企业通过独立实例、数据库、账号和插件配置隔离。
- [x] 插件随宿主 / 客户端构建；平台开放 / 停用与个人启用 / 停用分离，均保留个人配置和资产，平台重新开放保留原个人选择。
- [x] 管理员仅负责平台插件，不默认负责账号 / 角色维护，不获得个人配置、资产或业务审计访问特权。
- [x] 已开放插件对所有用户可用，个人配置与资产仅属于本人；首版不提供团队资产共享或跨用户资产授权。
- [x] 插件可仅支持 Web、仅支持 App 或支持两端。
- [x] 用最小示例插件验证授权、跨端数据、审计、启停和恢复。

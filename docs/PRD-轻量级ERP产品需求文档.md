## 1. 产品概述

### 1.1 产品定位

面向目前使用 Excel 记录业务或商品信息的小公司、小商铺的开源、自托管、插件化 ERP 平台。Web 端用于完整管理，App 端用于现场采集及必要的查询，两端共用后端业务 API，由后端统一执行认证、RBAC、个人资产归属和数据校验。

每家公司 / 商铺独立部署一套实例，独立管理数据库、账号和插件配置。项目不提供 SaaS 或厂商云平台，不提供同一实例的多企业管理、企业切换或跨企业管理后台。

产品不只是将 Excel 表格搬到网页，而是逐步减少手工录入、连接数据采集与业务管理。扫描、照片识别、商品、销售、库存以及客户、合同、项目等具体能力由业务或集成插件提供，不进入平台核心。

第一阶段优先跑通平台底座，用最小示例插件验证同一用户跨端访问个人数据、授权、平台插件开放 / 停用、个人插件启停与审计，不承诺完整行业业务系统。具体采集对象、识别方式与业务流程在后续插件需求中定义。

------------------------------------------------------------------------

### 1.2 产品愿景

让小团队能够以较低的部署、学习和维护成本，拥有一套可掌控数据、可按需组合、可持续扩展的经营系统。

### 1.3 产品使命

-   让企业能够自托管核心业务系统，掌控数据和部署环境。
-   让用户按需启用平台已开放的业务模块并保存个人配置，而不是被固定的一体化功能束缚。
-   让非开发人员通过受控配置调整字段、表单和业务流程。
-   让第三方开发者通过稳定的插件契约扩展平台能力。
-   让系统随着团队成长逐步扩展，而不要求早期一次性采购或实施大型 ERP。

### 1.4 产品原则

1.  **核心精简**：平台核心只提供跨模块共用的基础能力，不承载所有业务。
2.  **按需组合**：业务模块可以独立启用，模块之间通过公开契约协作。
3.  **配置优先**：常见变化优先使用元数据和规则配置，不要求修改源代码。
4.  **明确边界**：模块拥有自己的业务规则和数据写入职责。
5.  **独立自托管**：企业自行部署和维护，核心功能可无外网运行，不依赖厂商云平台、账号或在线授权。
6.  **渐进式生态**：先验证官方插件，再完善第三方插件开发和分发规范，不建设云端运营平台。
7.  **安全默认**：权限控制、个人资产隔离、审计、升级和备份属于平台基础能力；平台插件管理员无个人资产访问特权，不同企业通过独立部署隔离。
8.  **避免过度架构**：初期采用模块化单体，不为尚未验证的规模提前引入微服务。

## 2. 目标用户与场景

### 2.1 目标用户

-   使用 Excel 手工记录业务、商品或经营信息的小公司、小商铺。
-   希望减少重复录入、统一管理数据，并按需扩展功能的经营者。
-   需要自托管业务数据的小型企业。

具体行业、团队规模和首个正式业务插件仍需后续用户验证，不再限定为软件外包团队。

| 角色 | 主要诉求 |
| --- | --- |
| 平台插件管理员 | 管理平台插件的登记、配置、开放、停用与受控更新，不访问用户个人资产 |
| 普通用户 | 启用已开放插件，维护个人配置，在授权范围内采集、查询和管理自己的资产 |
| 插件开发者 | 通过公开契约扩展业务、Web 与 App 入口 |
| 自托管运维人员 | 部署、升级、备份和恢复系统 |

角色名称只是建议，实际操作能力由 RBAC 决定，数据访问范围由个人资产归属决定，不由客户端类型决定。自托管运维职责与平台插件管理员职责分开。

### 2.2 核心痛点

1.  业务或商品信息依赖 Excel 手工录入，重复操作多。
2.  现场采集与后台管理脱节，数据需要再次整理或转录。
3.  不同公司的管理需求不同，固定功能难以按需组合。
4.  同一平台上的用户需要独立选择插件，并确保个人配置与资产不会被其他用户访问。
5.  自行开发的定制系统难以复用和持续维护。

这些是当前需求假设，减少录入的具体效果需在正式业务插件阶段验证。

### 2.3 典型用户故事

-   作为平台插件管理员，我希望管理平台插件配置、开放与停用，让用户能够使用已开放的插件能力，但不查看或操作用户个人资产。
-   作为用户，我希望独立选择已开放的插件并保存自己的配置，不影响其他用户。
-   作为用户，我希望通过 App 完成插件支持的现场采集，并在提交前确认结果。
-   作为用户，我希望在 Web 端查看和管理自己通过 App 提交的数据，而不需要再次录入。
-   作为用户，我希望即使其他人拥有相同插件操作权限，也无法访问我的配置和业务资产。
-   作为开发者，我希望通过稳定契约提供业务 API 和适用端的界面，不修改其他模块内部实现。
-   作为自托管运维人员，我希望核心能力不依赖厂商云端，并能备份和升级系统。

## 3. 产品范围

### 3.1 平台核心能力

第一阶段必须交付：

-   单实例企业基础信息、用户账号与独立个人工作空间（账号维护机制待确认）
-   统一账号、登录、退出与会话管理
-   RBAC、插件权限登记、后端操作授权与强制个人资产归属校验
-   Web 和 App 的应用框架、导航及插件入口
-   共用业务 API、API 文档和统一错误语义
-   插件注册、依赖与兼容性校验、平台开放 / 停用与个人启用 / 停用及配置
-   核心与插件的数据迁移记录
-   关键操作审计、配置与健康检查
-   初始化、部署、升级、备份和恢复

自定义字段、表单设计、通用工作流、文件存储、通知和事件等共享能力按实际插件需求逐步建设，不作为首版完整引擎交付。

平台核心不直接承担扫码识别、商品、库存、CRM、项目或合同等完整业务规则。

### 3.2 业务插件方向

以下仅是后续能力方向，不代表 MVP 承诺或已确定的交付顺序：

| 插件方向 | 可能职责 |
| --- | --- |
| 采集与识别 | 扫码、拍照、解析或识别、结果确认与业务提交 |
| 商品与经营管理 | 商品、销售、库存等特定业务规则 |
| 客户与服务管理 | 客户、合同、项目、回款等特定业务规则 |
| 集成 | Excel 数据导入、外部系统连接、邮件或协作工具通知 |
| 报表与自动化 | 经营报表、触发规则、AI 辅助 |

MVP 只提供一个最小示例插件以验证平台契约。示例插件不是商品、财务或项目管理产品。

### 3.3 Skill 管理：插件化实现，独立产品能力

Skill 管理在产品上独立于插件中心：提供一级导航、专属列表 / 编辑 / 版本页面、独立权限和资产生命周期。一个 Skill 是可复用内容资产，不是一个 ERP 插件；插件中心只负责 Skill 管理插件自身的注册、兼容性和启停。

该能力复用平台认证、RBAC、审计与数据基础，不依赖正式业务插件或 AI 执行器。业务插件停用不影响 Skill 内容管理；Skill 管理插件自身停用则遵循平台入口隐藏、API 拒绝与数据保留规则。“独立”不默认指独立服务或独立部署。

本稿暂将 Skill 定义为 AI / Agent 可复用规范，具体定义与排期待确认。资产管理与后续执行集成分别规划，不自动扩大平台底座 MVP。详见《[Skill 管理插件 PRD](./plugins/PRD-Skill管理插件.md)》。

### 3.4 明确不属于早期范围的内容

-   完整的扫码、OCR 或其他识别业务插件
-   完整商品、销售、库存、CRM、合同、项目和回款系统
-   通用自定义字段 / 表单引擎、工作流与审批设计器
-   完整会计系统、复杂制造仓储、供应链及 HRM
-   任意代码脚本执行和通用低代码平台
-   任意第三方后端代码热加载或移动端运行时下载执行任意插件代码
-   微服务拆分与复杂分布式部署
-   企业共享空间、团队共享资产及跨用户资产授权
-   个人任意上传或安装插件代码
-   完整插件市场、付费与商业结算系统
-   SaaS、多租户托管、跨企业管理和厂商云平台
-   强制依赖厂商云端账号或在线授权

App 平台壳与示例插件入口属于首版范围；是否采用原生或跨平台技术、支持哪些移动系统，另行确认。

## 4. 产品信息架构

### 4.1 Web 管理端

-   登录与初始化
-   工作台 / 插件入口概览
-   个人工作空间与插件配置
-   个人插件中心；平台插件管理员另有平台插件管理入口
-   Skill 管理（后续独立能力入口，非插件中心子页面；以启用状态与 Skill 权限控制）
-   个人审计记录与个人设置；平台插件管理审计单独展示
-   平台已开放、本人已启用且有权限访问的插件页面

经营报表、客户、商品等内容由插件贡献，不在平台工作台中硬编码。

### 4.2 App 采集端

-   自部署 API 地址配置、登录、个人工作空间和个人设置
-   个人插件中心：查看已开放插件、维护本人启用状态与配置
-   平台已开放、本人已启用、适用于 App 且有权限访问的插件入口
-   示例插件的最小录入与查询界面
-   后续由插件提供的现场采集、确认与提交界面

不要求将完整管理后台搬到手机，也不要求每个插件同时提供两端界面。App 连接企业自行部署的后端 API，不依赖厂商云服务，也不维护第二套业务数据或授权规则。

### 4.3 跨端一致性

-   同一用户的 Web 和 App 操作同一份个人业务资源，不表示不同用户共享数据。
-   业务导航由平台开放状态、个人启用状态、插件适用端与用户权限共同决定；个人插件中心提供独立启用入口。
-   权限变更或插件停用后，后端必须在后续请求中拒绝未授权操作。
-   前端缓存、隐藏按钮或入口不能作为安全边界。

## 5. 核心流程

### 5.1 首版平台验证闭环

1.  初始化实例，建立用户账号、个人工作空间与角色权限绑定。
2.  平台插件管理员登记、配置并开放最小示例插件，校验依赖与兼容性。
3.  用户独立启用已开放插件并保存个人配置，不能修改平台配置或其他人的配置。
4.  Web 和 App 按平台开放状态、个人启用状态、适用端与操作权限显示入口。
5.  用户通过一端提交属于自己的示例记录，在另一端查询同一记录。
6.  后端校验身份、可信用户上下文、两级插件状态、RBAC、资产所有者和数据，关键操作写入分域审计。
7.  验证其他用户以及平台插件管理员无法访问该用户的配置、记录或业务审计。
8.  个人停用只关闭本人的入口与业务 API；平台停用关闭所有用户的该插件入口与业务 API。
9.  重新开放后仍按原个人启用状态生效；本人重新启用后原配置与资产可用，备份恢复后状态、归属与数据一致。

该闭环用于验证 ERP 平台运行逻辑，不替代后续真实业务价值验证。

### 5.2 模块组合流程

1.  平台插件管理员查看随系统部署的插件、版本、依赖、适用端和权限。
2.  平台检查兼容性、依赖和迁移结果，管理员配置平台级参数并开放插件。
3.  已开放插件能力对所有用户可用；用户按需独立启用、停用与保存个人配置。
4.  RBAC 控制可执行的操作，但相同操作权限不意味着可以访问其他用户的资产。
5.  平台开放 / 停用、个人启用 / 停用与资产删除分离；两级停用均拒绝对应范围的业务 API 并保留数据。

共享的是插件能力与平台允许共享的默认配置，不是个人配置、凭证或业务资产。平台默认配置可用于个人配置初始化；平台更新不覆盖已有个人配置，具体规则另行确认。

首版不提供在线安装任意代码。依赖校验分别覆盖平台开放与个人启用范围；存在有效依赖方时不得直接停用被依赖插件，应提示先处理依赖。卸载与删除数据是独立的后续能力。

### 5.3 后续采集与业务闭环

采集插件可采用“扫描 / 拍照 → 解析或识别 → 确认与修正 → 提交业务记录”的流程。采集权限不自动等于最终业务提交权限。

商品、销售、库存以及“客户 → 合同 → 项目 → 回款”等流程作为后续插件方向保留，具体数据与规则另写插件 PRD，不作为首版验收。

## 6. 自定义能力设计

本节为后续演进方向，不属于首版平台底座的必须交付范围。

### 6.1 自定义层级

#### L1：数据与界面配置

-   自定义字段
-   字段类型与校验
-   表单布局
-   列表列配置
-   筛选与排序配置
-   字段显示条件

#### L2：业务流程配置

-   状态定义
-   合法状态转换
-   角色 / 用户审批
-   条件判断
-   通知动作
-   受限的模块动作

#### L3：开发者扩展

-   新业务实体
-   新页面与路由
-   后端 API
-   事件订阅
-   外部系统集成
-   插件自有数据库迁移

### 6.2 配置边界

-   自定义字段定义属于元数据，需要版本化和审计。
-   核心标识、资产所有者、操作人、权限字段、金额等关键字段不能被无约束地覆盖；配置不得修改或绕过资产归属。
-   工作流规则采用受限 DSL 或结构化 JSON，不直接执行任意 SQL
    或任意脚本。
-   删除字段、修改字段类型和卸载插件前，应提示数据影响并执行可审计的迁移流程。
-   自定义配置应支持导出与备份，避免被锁定在单一实例中。

## 7. 插件生态与扩展模型

### 7.1 插件分类

1.  **业务插件**：商品、销售、库存、CRM、项目、合同、回款等。
2.  **集成插件**：邮件、企业微信、飞书、电子签章等。
3.  **采集与识别插件**：扫码、拍照识别、结果确认与提交等。
4.  **自动化 / AI 插件**：通知规则、报告生成、业务数据问答等。
5.  **独立能力插件**：Skill 管理等，使用插件契约接入，但有独立产品入口、权限和资产生命周期，不作为插件中心的内容管理子功能。

### 7.2 插件契约

完整插件 manifest 契约方向包含：

-   唯一 ID
-   名称、描述、作者
-   插件版本
-   平台 API 兼容版本
-   插件类型
-   依赖与冲突关系
-   权限声明
-   适用端（Web、App 或两端）
-   各端菜单、路由、页面动作等贡献点
-   后端 API 与服务注册信息
-   事件订阅与发布声明
-   数据库迁移信息
-   生命周期钩子
-   发布包校验和 / 签名元数据

上述是完整契约方向。首版至少覆盖 ID、版本、平台兼容性、依赖、权限、适用端、导航、后端注册与迁移；事件、生命周期扩展和发布包签名按后续需求建设。正式 schema 由单独的插件 SDK / 技术设计文档定义。

### 7.3 插件运行模型

#### 初期

-   官方插件与宿主一起构建、部署。
-   插件通过统一接口注册路由、权限和服务；事件订阅按后续需求扩展。
-   Web 和 App 依据插件元数据注册各自支持的导航与扩展点。
-   首版客户端插件随对应客户端构建，不要求运行时安装任意 UI 代码。
-   插件不允许任意访问宿主内部实现或其他模块数据库表。

#### 后续

-   建立插件 SDK、脚手架、测试工具和发布规范。
-   支持独立插件服务，通过受限 HTTP / RPC 与宿主交互。
-   插件分发规范提供版本、依赖、权限、兼容性和来源校验，不要求云端插件平台。
-   只有在安全模型成熟后，才考虑更动态的安装执行机制。

### 7.4 插件生命周期

首版实现登记、平台开放 / 停用和个人启用 / 停用及配置；平台插件管理员只负责平台级插件管理，安装、升级通过受控系统发布和迁移完成，不要求独立插件安装器。后续完整生命周期需区分以下状态与操作：

-   已发现 / 已登记
-   已安装
-   已启用
-   已停用
-   可升级 / 升级中 / 升级失败
-   卸载中 / 已卸载

安装、平台开放、个人启用、运行和卸载不是同一动作。个人停用只影响本人，平台停用影响全部用户；两者均保留个人配置、资产及归属，重新开放不改变原个人启用选择。删除数据必须明确提示、确认并具备备份或恢复策略，不因管理员管理平台插件而获得删除个人资产的权限。

### 7.5 插件安全

-   插件权限最小化。
-   服务端每次业务请求都执行身份、账号状态、平台开放状态、个人启用状态、RBAC 操作权限和个人资产归属校验；插件目录及本人启停 / 配置接口独立授权。
-   插件不能直接操作其他模块的数据表。
-   插件包需校验来源和完整性。
-   对独立服务插件设置网络、密钥、资源和访问权限边界。
-   签名只能证明来源与完整性，不能证明代码绝对安全。
-   提供漏洞报告、撤回、兼容性公告和安全更新机制。

## 8. 数据与权限原则

### 8.1 个人工作空间与资产隔离

-   首版以个人工作空间作为业务隔离边界，每家公司 / 商铺仍独立部署一套实例；实例内的多个用户不共享业务资产，首版不提供团队资产共享。
-   个人插件配置、业务记录和后续附件等资产归本人所有，必须包含可靠的所有者归属，或通过可靠关联确定归属。
-   用户上下文由服务端认证确定，不能信任客户端提交的用户 / 所有者 ID；创建记录时由服务端写入归属，首版不提供资产转移。
-   列表、详情、创建、更新、删除、业务审计、后台任务和事件消费者均需执行个人归属校验，不能仅按插件权限放行。
-   平台插件管理员只管理平台插件，不具备用户个人配置、业务资产或业务审计的应用 / API 访问权限，不设置默认管理员绕过。
-   这里的隔离约束是应用与 API 层面的权限边界，不承诺阻止掌握服务器、数据库或备份访问权的自托管运维人员读取底层数据。

### 8.2 数据存储策略

-   PostgreSQL 作为主要业务数据库。
-   稳定核心字段采用关系型列。
-   自定义字段采用受控元数据 + JSONB 或扩展字段表。
-   关键金额、状态、权限和关联字段不应全部放进 JSONB。
-   文件内容与文件元数据分离，存储接口支持本地文件系统，后续可扩展对象存储。
-   数据库迁移按核心和插件分别记录版本。

### 8.3 权限模型

初期采用 RBAC：角色绑定权限，插件声明业务权限；账号开通、角色绑定及其维护机制待确认，不默认由平台插件管理员负责。Web 与 App 使用同一授权规则，不能因客户端类型不同获得额外权限。

RBAC 控制“能做什么”，个人资产归属控制“可以访问谁的数据”。首版必须同时执行两者；复杂行级 / 字段级权限配置引擎另行定义，但不能将所有者校验推迟到后续版本。

-   **平台插件管理员**：仅管理平台插件的登记、配置、开放、停用与受控更新；该角色不包含个人业务资产访问权限，也不负责账号、角色或个人插件配置管理。
-   **普通用户**：按权限使用已开放插件，管理本人启用状态、个人配置与资产；不能修改平台插件设置。
-   **业务操作权限**：插件按查询、创建、编辑、删除等操作分别声明权限，不赋予跨用户访问能力。
-   **个人资产归属**：即使拥有某项操作权限，也只能访问属于本人的资产；平台插件管理员角色不能豁免该检查。管理员如同时拥有普通用户权限，也只能使用自己的个人空间。

业务访问条件：有效身份与账号状态 + 平台已开放 + 本人已启用 + 对应操作权限 + 本人资产归属（创建时由后端指定所有者）。插件目录与本人启停 / 配置接口独立校验身份、状态与操作权限，不能要求已启用才允许执行首次启用。

权限检查应覆盖菜单显示、API、数据查询、事件处理和后台任务；前端隐藏按钮不能替代后端授权。

### 8.4 审计

至少记录：

-   登录和认证相关事件
-   账号状态、角色和权限变更（维护机制待确认）
-   平台插件安装、配置、开放 / 停用、升级和卸载
-   个人插件启用 / 停用与配置变更
-   关键业务数据的创建、更新和删除
-   工作流状态与审批动作
-   系统配置和数据迁移操作

审计区分平台插件管理审计、个人业务审计和其他系统审计。平台插件管理员仅查看平台插件管理审计，普通用户仅查看本人业务审计，不能借审计读取其他用户资产或配置。账号 / 角色等其他系统审计的访问机制待确认，不默认开放给平台插件管理员。审计不存储业务正文、个人配置敏感值或凭证，记录应限制用户修改和删除。

## 9. 非功能性需求

### 9.1 部署与运维

-   提供 Docker Compose 部署方式。
-   提供 `.env.example` 与配置说明。
-   提供健康检查和启动失败的可读日志。
-   数据库、上传文件和必要配置应使用持久化卷。
-   提供备份、恢复、升级与回滚说明。
-   支持无外网环境使用核心业务能力。
-   首版插件随系统发布；后续支持受信任仓库或离线包安装。

### 9.2 安全

-   密码使用适当的密码哈希算法存储。
-   Cookie / Token 的认证策略需要在技术设计中明确。
-   防止跨用户访问个人配置与资产、管理员越权、CSRF（适用时）、XSS、注入和不安全文件上传。
-   密钥不得写入插件前端包或日志。
-   重要操作应有审计与确认机制。
-   插件更新与数据库迁移应有失败处理方案。

### 9.3 可维护性

-   核心与模块依赖方向明确。
-   公共 API 有版本约束与自动化兼容测试。
-   核心流程具备单元测试和集成测试。
-   数据库迁移可重复验证。
-   日志包含请求 ID、操作人标识（避免泄露敏感数据）和错误上下文。
-   插件故障不能无边界地破坏其他模块；后续独立进程插件应进一步隔离故障。

### 9.4 可用性与性能

MVP 阶段不预设未经验证的高并发指标。初期应优先保证： - 小公司、小商铺的常规管理操作流畅。 - 常用列表支持分页、筛选和排序。 -
报表查询有明确的数据范围与索引策略。 -
后台任务具备重试、幂等与失败记录。 -
通过真实用户数据和压测逐步建立性能目标。

-   新用户完成独立部署、初始化企业信息、个人空间和角色绑定的成功率与耗时

## 13. 版本路线

### V0：可运行的平台底座

-   企业基础信息、用户账号与个人空间、认证、RBAC、个人资产归属和分域审计
-   共用后端 API，Web 与 App 平台壳
-   编译时插件注册、依赖与兼容性校验、平台开放 / 停用、个人启停与配置
-   最小示例插件与跨端验证闭环
-   Docker Compose、升级、备份与恢复

### V1：真实业务与配置能力

-   根据用户验证选择首个真实业务插件，不预先承诺行业范围
-   逐步提供采集 / 识别、商品或客户经营能力
-   按实际需求建设自定义字段、表单、状态机与通知
-   验证减少手工录入的业务价值

### V2：开发者平台

-   完善插件 SDK、CLI、脚手架与契约测试工具
-   插件仓库索引和版本、签名、发布规范
-   Web 与 App 扩展契约的兼容性治理

### V3：开放生态

-   第三方插件提交与审核、独立服务插件
-   私有仓库与离线安装
-   完善插件文档、兼容性验证与离线分发，不建设云端交易或运营平台

## 15. 当前产品决策摘要

-   **产品定位**：面向使用 Excel 管理业务或商品信息的小公司、小商铺的开源、自托管 ERP 平台。
-   **部署边界**：一家公司 / 商铺独立部署一套实例，无 SaaS、厂商云平台或同实例多企业管理；App 连接企业自部署的 API。
-   **长期价值**：减少手工录入，以插件组合连接数据采集和业务管理。
-   **首版目标**：平台底座优先，用最小示例插件验证完整链路，不细化正式业务功能。
-   **多端形态**：Web 完整管理、App 现场采集；首版只交付平台壳和示例入口，App 技术选型待定。
-   **统一后端**：共用业务 API，服务端统一执行认证、账号状态、两级插件状态、RBAC、个人资产归属和数据校验。
-   **插件策略**：随宿主 / 客户端构建注册；管理员仅负责平台插件，用户独立启停与配置；两级停用均保留个人配置和资产，重新开放保留个人选择；插件可只提供 Web、App 或两端界面。
-   **资产边界**：共享插件能力，独立个人配置，隔离个人资产；平台插件管理员没有个人资产访问特权。
-   **Skill 管理**：插件化实现、独立一级入口与资产管理，不绑定业务插件或 AI 执行器；独立排期，暂不纳入平台底座 MVP P0。
-   **MVP 主线**：初始化 → 个人空间与认证 → 平台开放插件 → 个人启用与配置 → 本人跨端访问记录 → RBAC / 归属校验与审计 → 两级停用 / 恢复。
-   **后续能力**：采集识别、商品经营、CRM / 合同 / 项目 / 回款、自定义字段和通用工作流。
-   **暂不做**：任意代码热加载、完整业务 ERP、完整插件市场及复杂分布式架构。

# 轻量级 ERP 产品需求文档（PRD）

-   **文档版本**：v0.1
-   **文档状态**：讨论稿 / 产品方向基线
-   **产品形态**：开源、自托管、模块化、插件化的团队经营管理平台
-   **目标用户**：5--30 人的小型技术团队、软件外包公司、数字工作室
-   **技术方向**：React + TypeScript 前端；Go 后端；PostgreSQL；Docker
    Compose

> 本文用于明确产品愿景、目标用户、业务范围、产品原则、核心能力和长期演进方向。具体
> MVP 交付范围以配套《MVP-PRD》为准。

------------------------------------------------------------------------

## 1. 产品概述

### 1.1 产品定位

面向小型技术团队、软件外包公司和工作室的开源、自托管、可组合业务管理平台。用户从最小业务模块开始，通过安装插件、配置字段和工作流，逐步搭建适合自身经营方式的系统。

产品不是试图在第一版复制大型 ERP
的全部能力，而是降低小团队建立统一经营管理系统的成本，解决客户、合同、项目、交付和回款数据分散、流程依赖人工衔接的问题。

### 1.2 产品愿景

让小团队能够以较低的部署、学习和维护成本，拥有一套可掌控数据、可按需组合、可持续扩展的经营系统。

### 1.3 产品使命

-   让企业能够自托管核心业务系统，掌控数据和部署环境。
-   让用户按需安装业务模块，而不是被固定的一体化功能束缚。
-   让非开发人员通过受控配置调整字段、表单和业务流程。
-   让第三方开发者通过稳定的插件契约扩展平台能力。
-   让系统随着团队成长逐步扩展，而不要求早期一次性采购或实施大型 ERP。

### 1.4 产品原则

1.  **核心精简**：平台核心只提供跨模块共用的基础能力，不承载所有业务。
2.  **按需组合**：业务模块可以独立启用，模块之间通过公开契约协作。
3.  **配置优先**：常见变化优先使用元数据和规则配置，不要求修改源代码。
4.  **明确边界**：模块拥有自己的业务规则和数据写入职责。
5.  **自托管优先**：核心功能不依赖必须连接厂商云端才能运行。
6.  **渐进式生态**：先验证官方插件，再开放第三方插件市场。
7.  **安全默认**：租户隔离、权限控制、审计、升级和备份属于平台基础能力。
8.  **避免过度架构**：初期采用模块化单体，不为尚未验证的规模提前引入微服务。

## 2. 目标用户与场景

### 2.1 目标用户

#### 主要用户群

-   5--30 人的软件外包公司
-   小型软件开发团队
-   数字营销、设计、咨询等服务型工作室
-   需要自行部署业务系统、重视数据控制权的小型企业

#### 典型角色

  角色                  主要诉求
  --------------------- ------------------------------------------
  企业负责人 / 管理员   查看经营情况、管理成员与权限、配置系统
  销售 / 客户负责人     管理客户、联系人、跟进记录与商机
  项目负责人            管理项目、任务、里程碑和交付进度
  合同 / 财务协作人员   维护合同、收款计划和回款记录
  普通成员              查看被授权的客户、项目、任务和待办
  插件开发者            使用 SDK 与公开 API 开发、测试、发布插件
  自托管运维人员        部署、升级、备份、恢复和管理插件来源

### 2.2 核心痛点

1.  客户、项目、合同和回款信息散落在不同工具与表格中。
2.  客户签约后，合同、项目交付和回款缺乏统一关联。
3.  团队需要定制字段、状态和审批流程，但不希望每次调整都改代码。
4.  传统 ERP 的实施、维护和学习成本对小团队过高。
5.  单体 SaaS 工具不容易满足数据自托管和私有部署需求。
6.  自行开发的定制系统难以复用，升级后容易产生维护负担。

### 2.3 典型用户故事

-   作为企业负责人，我希望查看客户、项目进度和应收款的概览，以判断当前经营状态。
-   作为销售，我希望记录客户、联系人、跟进和商机，并能把客户转为合同或项目。
-   作为项目负责人，我希望将项目关联客户与合同，并跟踪任务和里程碑。
-   作为合同协作人员，我希望维护合同金额、收款计划和回款记录。
-   作为管理员，我希望按需启用业务模块，并控制不同成员可以访问的能力。
-   作为管理员，我希望添加客户自定义字段、调整项目状态和设置简单审批规则。
-   作为开发者，我希望在不修改宿主核心代码的前提下开发一个插件。
-   作为自托管管理员，我希望离线或内网环境也能使用核心功能，并能备份和升级系统。

## 3. 产品范围

### 3.1 平台核心能力

平台核心应提供多个业务模块共用的基础设施：

-   企业空间 / 租户管理
-   用户、成员邀请与角色权限
-   登录与会话管理
-   菜单、路由与工作台框架
-   插件清单注册、依赖和兼容性元数据
-   字段与表单元数据基础
-   通知与待办基础设施
-   审计日志
-   文件元数据与存储接口
-   领域事件基础设施
-   配置管理
-   API 文档与健康检查
-   部署、备份和升级机制

平台核心不应直接承担 CRM、项目、合同等领域的完整业务逻辑。

### 3.2 官方业务模块方向

  模块           主要职责                       依赖 / 关联
  -------------- ------------------------------ --------------------
  CRM 客户管理   客户、联系人、跟进、商机       平台核心
  项目管理       项目、任务、里程碑、负责人     可关联 CRM
  合同管理       合同基本信息、金额、交付约定   可关联客户、项目
  回款管理       收款计划、收款记录、逾期状态   可关联合同
  工作流         状态流转、条件、审批、动作     平台核心与业务模块
  通知集成       邮件、企业协作工具等外部通知   以集成插件方式扩展
  报表与自动化   经营报表、触发规则、AI 辅助    后续阶段

### 3.3 明确不属于早期范围的内容

-   完整会计系统、凭证、总账、税务申报
-   制造业 MRP、复杂仓储和供应链
-   薪酬、考勤、绩效等完整 HRM
-   全功能敏捷研发管理工具
-   任意代码脚本执行和通用低代码平台
-   第一版即支持任意第三方后端代码热加载
-   微服务拆分与复杂分布式部署
-   插件付费、分账、退款等完整商业结算系统
-   强制依赖厂商云端账号或在线授权才能使用核心业务

## 4. 产品信息架构

### 4.1 一级导航建议

-   工作台
-   客户管理（插件）
-   项目管理（插件）
-   合同管理（插件）
-   回款管理（插件）
-   待办与通知
-   插件中心
-   系统设置

实际导航应由平台基础入口与当前企业已启用的插件共同生成。无权限或未启用的模块不应展示为可操作入口。

### 4.2 工作台

工作台用于汇总当前用户有权限查看的信息，初期包括：

-   我的待办
-   我负责的项目
-   最近跟进的客户
-   待审批事项（若启用审批）
-   近期应收款概览（若启用回款模块）
-   最近活动记录

仪表盘数据必须遵守租户隔离与行级权限规则。

## 5. 核心业务流程

### 5.1 客户到回款流程

1.  创建客户与联系人。
2.  记录客户跟进和商机状态。
3.  商机确认后创建合同或报价记录。
4.  合同关联客户，可选关联项目。
5.  项目创建任务与里程碑，跟踪交付。
6.  合同配置收款计划。
7.  记录实际回款，并更新未收金额和逾期状态。
8.  工作台汇总项目进度和应收款信息。

该流程用于验证模块之间的业务关联，但各模块仍需保持独立职责。具体事务边界和跨模块调用规则应由技术设计文档明确。

### 5.2 模块组合流程

1.  管理员进入插件中心。
2.  查看插件介绍、版本、依赖、权限和兼容性。
3.  安装或启用官方插件。
4.  平台检查依赖、版本和数据库迁移要求。
5.  为指定企业启用插件并注册其菜单、权限和扩展点。
6.  管理员配置字段、角色和流程。
7.  插件停用时保留业务数据；卸载数据必须有单独、明确的操作和备份提示。

## 6. 自定义能力设计

### 6.1 自定义层级

#### L1：数据与界面配置

-   自定义字段
-   字段类型与校验
-   表单布局
-   列表列配置
-   筛选与排序配置
-   字段显示条件

#### L2：业务流程配置

-   状态定义
-   合法状态转换
-   角色 / 用户审批
-   条件判断
-   通知动作
-   受限的模块动作

#### L3：开发者扩展

-   新业务实体
-   新页面与路由
-   后端 API
-   事件订阅
-   外部系统集成
-   插件自有数据库迁移

### 6.2 配置边界

-   自定义字段定义属于元数据，需要版本化和审计。
-   核心标识、租户 ID、权限字段、金额等关键字段不能被无约束地覆盖。
-   工作流规则采用受限 DSL 或结构化 JSON，不直接执行任意 SQL
    或任意脚本。
-   删除字段、修改字段类型和卸载插件前，应提示数据影响并执行可审计的迁移流程。
-   自定义配置应支持导出与备份，避免被锁定在单一实例中。

## 7. 插件生态与扩展模型

### 7.1 插件分类

1.  **业务插件**：CRM、项目、合同、回款等。
2.  **集成插件**：邮件、企业微信、飞书、电子签章等。
3.  **自动化 / AI 插件**：通知规则、报告生成、业务数据问答等。

### 7.2 插件契约

插件 manifest 至少需要声明：

-   唯一 ID
-   名称、描述、作者
-   插件版本
-   平台 API 兼容版本
-   插件类型
-   依赖与冲突关系
-   权限声明
-   菜单、路由、页面动作等贡献点
-   事件订阅与发布声明
-   数据库迁移信息
-   生命周期钩子
-   发布包校验和 / 签名元数据

正式 schema 由单独的插件 SDK / 技术设计文档定义。

### 7.3 插件运行模型

#### 初期

-   官方插件与宿主一起构建、部署。
-   插件通过统一接口注册路由、权限、服务和事件订阅。
-   前端依据插件元数据注册导航与扩展点。
-   插件不允许任意访问宿主内部实现或其他模块数据库表。

#### 后续

-   建立插件 SDK、脚手架、测试工具和发布规范。
-   支持独立插件服务，通过受限 HTTP / RPC 与宿主交互。
-   插件市场提供版本、依赖、权限、兼容性和来源校验。
-   只有在安全模型成熟后，才考虑更动态的安装执行机制。

### 7.4 插件生命周期

需区分以下状态与操作：

-   已发现 / 已登记
-   已安装
-   已启用
-   已停用
-   可升级 / 升级中 / 升级失败
-   卸载中 / 已卸载

安装、企业启用、运行和卸载不是同一动作。停用默认不删除业务数据；删除数据必须明确提示、确认并具备备份或恢复策略。

### 7.5 插件安全

-   插件权限最小化。
-   服务端每次请求都执行身份、租户和资源权限校验。
-   插件不能直接操作其他模块的数据表。
-   插件包需校验来源和完整性。
-   对独立服务插件设置网络、密钥、资源和访问权限边界。
-   签名只能证明来源与完整性，不能证明代码绝对安全。
-   提供漏洞报告、撤回、兼容性公告和安全更新机制。

## 8. 数据与权限原则

### 8.1 多租户

-   企业空间是默认业务隔离边界。
-   业务数据应包含租户归属，或通过可靠的关联关系确定归属。
-   租户上下文由服务端认证与授权流程确定，不能信任客户端自行提交的租户
    ID。
-   查询、更新、删除、后台任务和事件消费者均需执行租户隔离。
-   管理员跨租户操作必须显式授权并记录审计。

### 8.2 数据存储策略

-   PostgreSQL 作为主要业务数据库。
-   稳定核心字段采用关系型列。
-   自定义字段采用受控元数据 + JSONB 或扩展字段表。
-   关键金额、状态、权限和关联字段不应全部放进 JSONB。
-   文件内容与文件元数据分离，存储接口支持本地文件系统，后续可扩展对象存储。
-   数据库迁移按核心和插件分别记录版本。

### 8.3 权限模型

初期采用角色为主的权限模型：

-   平台 / 实例管理员
-   企业管理员
-   普通成员
-   模块级权限
-   资源级权限（例如仅查看自己负责的项目）

权限检查应覆盖菜单显示、API、数据查询、事件处理和后台任务；前端隐藏按钮不能替代后端授权。

### 8.4 审计

至少记录：

-   登录和认证相关事件
-   成员、角色和权限变更
-   插件安装、启停、升级和卸载
-   关键业务数据的创建、更新和删除
-   工作流状态与审批动作
-   系统配置和数据迁移操作

审计记录应限制普通用户修改和删除。

## 9. 非功能性需求

### 9.1 部署与运维

-   提供 Docker Compose 部署方式。
-   提供 `.env.example` 与配置说明。
-   提供健康检查和启动失败的可读日志。
-   数据库、上传文件和必要配置应使用持久化卷。
-   提供备份、恢复、升级与回滚说明。
-   支持无外网环境使用核心业务能力。
-   支持从受信任仓库或离线包安装插件。

### 9.2 安全

-   密码使用适当的密码哈希算法存储。
-   Cookie / Token 的认证策略需要在技术设计中明确。
-   防止越权访问、租户穿透、CSRF（适用时）、XSS、注入和不安全文件上传。
-   密钥不得写入插件前端包或日志。
-   重要操作应有审计与确认机制。
-   插件更新与数据库迁移应有失败处理方案。

### 9.3 可维护性

-   核心与模块依赖方向明确。
-   公共 API 有版本约束与自动化兼容测试。
-   核心流程具备单元测试和集成测试。
-   数据库迁移可重复验证。
-   日志包含请求 ID、租户上下文标识（避免泄露敏感数据）和错误上下文。
-   插件故障不能无边界地破坏其他模块；后续独立进程插件应进一步隔离故障。

### 9.4 可用性与性能

MVP 阶段不预设未经验证的高并发指标。初期应优先保证： - 5--30
人团队的常规业务操作流畅。 - 常用列表支持分页、筛选和排序。 -
报表查询有明确的数据范围与索引策略。 -
后台任务具备重试、幂等与失败记录。 -
通过真实用户数据和压测逐步建立性能目标。

## 10. 商业与生态方向

尽管产品以开源自托管为基础，未来可以探索：

-   官方托管版
-   企业支持与升级服务
-   官方高级插件
-   插件市场交易与开发者分成
-   企业集成与迁移服务
-   备份监控、团队协作和管理增强能力

商业化不应成为 MVP
的阻塞项。先验证用户是否持续使用核心业务闭环、是否愿意安装模块，以及开发者是否能独立开发插件。

## 11. 产品成功指标

早期以验证性指标为主：

-   新用户完成部署并创建首个企业空间的成功率
-   用户首次完成"客户 → 合同 → 项目 → 回款记录"闭环所需时间
-   官方模块启用率和跨模块关联使用率
-   用户自定义字段与流程的使用率
-   升级、备份与恢复成功率
-   插件 SDK 示例项目从创建到运行的耗时
-   第三方插件在不修改宿主核心代码情况下通过测试的比例
-   用户持续使用和主动反馈情况

不要在没有实际用户数据前预设过于具体的增长目标。

## 12. 主要风险与应对

  ------------------------------------------------------------------------------------
  风险                                应对
  ----------------------------------- ------------------------------------------------
  范围不断膨胀                        聚焦小型技术团队与工作室，优先跑通经营闭环

  自定义能力演变成完整低代码平台      分层实现，先字段和状态，再审批与动作

  插件高度耦合                        统一 API、事件、权限和迁移契约

  第三方插件带来安全风险              初期只允许受信任插件，后续采用受限 API /
                                      独立进程

  数据结构过度动态化                  核心字段关系型化，自定义字段受控存储

  自托管升级困难                      Compose、迁移版本、备份、升级检查与恢复说明

  开源生态缺少开发者                  先完善 SDK、文档、脚手架和示例插件

  单人开发维护压力大                  模块化单体、减少基础设施数量、优先验证真实需求

## 13. 版本路线

### V0：可用的经营系统

-   平台核心
-   CRM、项目、合同、回款基础模块
-   核心业务闭环
-   Docker Compose 部署

### V1：可组合和可配置

-   插件注册与启停
-   依赖和兼容性校验
-   自定义字段与表单
-   简单状态机和审批
-   事件与通知基础设施

### V2：开发者平台

-   插件 SDK 与 CLI
-   示例插件和测试工具
-   插件仓库索引
-   版本、签名与发布规范

### V3：开放生态

-   第三方插件提交与审核
-   独立服务插件
-   私有仓库与离线安装
-   插件评分、付费和商业分成（视需求决定）

## 14. 待决策事项

以下内容需要在技术设计或用户验证阶段确认：

1.  最终产品名称与品牌。
2.  开源协议及官方插件协议。
3.  认证采用 Cookie Session 还是 Token 方案。
4.  自定义字段采用 JSONB 还是扩展表的混合策略。
5.  第一版是否包含商机管理。
6.  工作流首版支持哪些触发器和动作。
7.  插件前端扩展采用静态构建注册还是独立远程资源。
8.  官方插件仓库格式与离线安装包格式。
9.  本地文件存储与对象存储接口边界。
10. 备份、升级和回滚的正式操作规范。

## 15. 当前产品决策摘要

-   **产品定位**：面向小型技术团队、软件外包公司和工作室的开源、自托管、可组合经营管理平台。
-   **核心价值**：按需组合模块，并通过配置自定义字段、表单和业务流程。
-   **技术方向**：React + TypeScript、Go、PostgreSQL、Docker Compose。
-   **后端架构**：模块化单体，明确领域边界。
-   **插件策略**：初期编译时注册 +
    稳定插件契约，后续逐步开放独立服务插件。
-   **数据策略**：核心字段关系型化，自定义字段受控元数据化。
-   **MVP 主线**：客户 → 合同 → 项目 → 回款。
-   **暂不做**：完整财务、复杂供应链、任意脚本执行、微服务化和完整插件交易平台。
